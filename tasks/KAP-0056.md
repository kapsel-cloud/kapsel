## Result

One read-only review maps Kapsel's current modules, interfaces, seams, adapters, authority, durable
state, recovery, dependency direction, configuration, and test surfaces. It produces a visual
temporary report, ranks concrete findings by evidence and timing, and recommends at most two
pre-KAP-0053 corrections. The repository records the accepted classification and next action; the
review itself changes no implementation.

This is not an invitation to redesign Kapsel, broaden the product, or optimize for line count. A
large deep module may be correct. A small shallow module may be harmful. Findings must demonstrate
lost locality, weak leverage, duplicated invariants, leaked authority, or a test seam that differs
from the production interface.

## Review language

Use these terms consistently:

- **Module:** an interface and its implementation.
- **Interface:** every fact a caller must know, including invariants, ordering, errors,
  configuration, and performance characteristics.
- **Depth:** leverage behind an interface.
- **Seam:** where an interface can alter behavior without editing callers.
- **Adapter:** a concrete implementation at a seam.
- **Leverage:** behavior callers receive per unit of interface they must understand.
- **Locality:** concentration of change, bugs, knowledge, and verification.

Apply the deletion test: if deleting a module makes complexity vanish, it is likely pass-through; if
complexity reappears across callers, the module is earning its depth. One adapter is a hypothetical
seam; two concrete adapters establish a real seam.

## Work

1. Read the scope, architecture, active experiment, accepted decisions, sandbox owners, KAP-0052,
   KAP-0055, KAP-0053, and their implementation/tests before drawing conclusions.
2. Map the production dependency and process graph from public sandbox admission through scheduler,
   private runner handoff, `Application`, gateway journal, terminal report, receipt publication,
   cleanup, retention, and public projection.
3. Map durable state and authority ownership. Identify every writer, reader, credential, lease,
   restart owner, and handoff between admission SQLite, per-run journal/outbox, immutable receipt

4. Review module depth and locality across the root package, `kapsel-sandbox`, native modes, runner
   handoff, storage/publication, tests, fixtures, and scripts. Do not infer shallowness from file
   size alone.
5. Review interface and test alignment. Flag behavior tested only through private helpers, repeated
   matrices that can disagree, production paths bypassed by fixtures, or tests that require broader
   interfaces than callers.
6. Review dependency direction and configuration. Flag cycles, duplicated domain language, ambient
   inputs, authority-bearing configuration spread across modules, or provider concerns leaking into
   provider-neutral code.
7. Apply the deletion test to every proposed extraction or consolidation. Identify existing seams
   with one adapter and reject speculative generalization unless a second concrete adapter already
   exists.
8. Produce a self-contained visual HTML report in the operating system's temporary directory. Give
   each candidate files, evidence, problem, proposed direction, benefits in leverage/locality, a
   before/after diagram, recommendation strength, and conflicts with accepted decisions.
9. Classify every candidate as:
   - `pre-KAP-0053 blocker`: a demonstrated authority, state, recovery, dependency, or
     test-integrity defect that provider composition would harden;
   - `deferred after sandbox operational evidence`: valuable but not required before GKE composition
     and safer after KAP-0053/KAP-0050 supplies operational evidence;
   - `reject`: cosmetic, speculative, generic, or unsupported by concrete friction.
10. Recommend at most two pre-KAP-0053 corrections and one top recommendation. If no blocker exists,
    say so and resume KAP-0053 without manufacturing refactor work.
11. In a separate supervisor decision, record the accepted classification in this packet. Give each
    selected correction its own finite implementation packet, owner, preservation tests, acceptance,

## Required evidence

The report must include:

- a package/module dependency diagram;
- a process and authority diagram;
- a durable-state ownership table;
- a restart/recovery responsibility table;
- an interface-to-test map for the critical sandbox path;
- concrete file and line references for every finding;
- the deletion-test result for every recommended module change;
- accepted-decision conflicts and whether reopening them is justified;
- explicit non-findings where a large or complex module is deep and should remain intact; and
- a sequencing recommendation for KAP-0053 and work deferred until sandbox operational evidence.

Use repository evidence, not raw line count, aesthetics, or generalized best practices. Validate any
reported dependency or call relationship against source and tests.

## Acceptance

- The review changes no source, test, contract, task, or configuration file; its only artifact is
  the temporary HTML report and its response summary.
- Every finding names concrete files/lines, current friction, affected interface, and violated
  locality or leverage.
- Every suggested module change passes the deletion test and identifies whether its seam has one or
  multiple concrete adapters.
- The report preserves KAP-0038 semantics, one active capability, request-only caller authority, and
  the accepted KAP-0055 state separation.
- Findings distinguish architecture integrity from live-provider uncertainty owned by KAP-0053.
- At most two corrections are classified as pre-KAP-0053 blockers.
- A fresh reviewer finds no unsupported finding, missed authority/state owner, or speculative
  abstraction in the report. If the author corrects a valid review finding, the same reviewer
  confirms the bounded fix against the final temporary report before completion.
- The supervisor records one outcome: `resume KAP-0053 unchanged`, `commission bounded corrections`,
  or `stop for owner conflict`.

## Non-goals

No source edit, refactor implementation, new crate, file-size target, generic provider/storage/queue
interface, naming campaign, formatting cleanup, public contract change, second capability, GKE
manifest, provider access, dependency upgrade, performance rewrite, v1 redesign, or production
claim.

## Residual risk

Static review can find structural contradictions and costly coupling, but it cannot establish live
isolation, operational simplicity, performance, failure behavior, or external usefulness. A clean
report does not make KAP-0053 safe; it only prevents known architecture debt from being silently
embedded into provider composition. Broad refactoring before operational evidence can reduce rather
than improve integrity, so optional findings remain deferred.
