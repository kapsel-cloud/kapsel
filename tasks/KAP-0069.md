# Reshape The Bounded Public Product Proof

Status: complete historical direction decision, superseded by accepted [KAP-0072](KAP-0072.md) and
[KAP-0073](KAP-0073.md). KAP-0070 later closed through fallback, so neither its serialized
native-host route nor its backup/restore guarantees remain active. No provider credential, resource,
spend, image, endpoint, DNS, or public traffic is authorized.

Problem: the accepted sandbox contracts, deterministic service, private runner handoff, and offline
deployment tranches contain substantial product and security evidence, but the paused Kubernetes-
hosted control topology has not passed live acceptance. Completing that topology would preserve
several controls but also retain separate system, scheduler, cleanup, and staging workloads whose
complexity is not required by a serialized public proof. Replacing the whole service would discard
more accepted semantics than it removes. One decision must distinguish the product proof from its
first deployment topology.

Contract owners: [public sandbox API](../docs/SANDBOX_API.md),
[sandbox deployment](../docs/SANDBOX_DEPLOYMENT.md), [architecture](../docs/ARCHITECTURE.md),
[threat model](../docs/THREAT_MODEL.md), [privacy boundary](../docs/PRIVACY.md), and
[V1 technical direction](../docs/VISION.md).

Depends on: verified v0.2.0 publication, accepted KAP-0051, KAP-0052, KAP-0055, and KAP-0056
evidence, and only KAP-0053's accepted offline tranches. No earlier provider fixture or acceptance
is execution authority.

## Decision inputs

The accepted semantic spine is:

```text
fixed scenario + idempotency key
  -> durable sandbox admission and opaque run identity
  -> bounded server-owned scheduling and authority
  -> separate native runner
  -> real Kapsel Application execute or same-operation reconcile
  -> exact terminal report and frozen receipt handoff
  -> reconnectable public projection
  -> independently observed cleanup and retention
```

KAP-0051 fixes the public contract. KAP-0052 implements durable admission, projection, scheduling,
receipt publication, retention, cleanup ownership, and the one-way `kapsel-sandbox -> kapsel`
dependency. KAP-0055 proves a separate provider-neutral runner and same-operation recovery without a
shared system-state volume. KAP-0053 then implemented substantial GKE execution composition but
stopped before a complete render, live enforcement, recovery, or public proof.

No live evidence currently establishes runtime or network isolation, key custody, storage identity,
cleanup under provider failure, traffic cutoff, saturation, bounded cost, exact recreation, or
public safety. The previous GKE fixture is incomplete and explicitly non-deployable.

## Product-essential properties

The selected proof retains these properties independent of deployment topology:

1. one durable public run identity, idempotent admission, reconnect, ordered replay, and exact
   receipt retrieval;
2. only fixed synthetic scenarios and server-owned target, authorization, trust, signing,
   Kubernetes, deadline, retention, and cleanup authority;
3. one conditional mutation opportunity through the real root `Application` and explicit
   `SUCCEEDED`, `FAILED`, or `UNKNOWN` receiver meaning;
4. intentional native runner process loss followed by same-operation reconciliation without a blind
   second mutation;
5. admission, anonymous rate, queue, active-run, resource, deadline, retained-byte, and cost bounds;
6. a durable global stop that blocks new admission while preserving reads, recovery, receipt
   retrieval, retention, and cleanup;
7. opaque locator handling, disclosure-minimal public projection, private state and key custody, and
   isolation from unrelated or prior runs;
8. UID- and owner-safe cleanup through serial capacity reuse, plus fail-closed host/storage-loss
   traffic withdrawal, teardown, complete provider/cluster/state absence, clean stopped recreation,
   readiness validation, and explicit admission reopening without visitor continuity; and
9. separate operation, receipt-availability, deadline, transport, and cleanup facts.

Kubernetes-hosting the admission database, receipt store, scheduler, cleanup controller, and key
stagers is not itself a product property. Neither are controller-state TLS, `TokenReview`, projected
controller tokens, Secret-to-Secret staging, or multi-Pod `ReadWriteOncePod` composition.

## Route comparison

| Route                            | Locality and reuse                                                                                                           | Deployment, public-risk, cost, and reproducibility                                                                                                  | Decision                                                                           |
| -------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| Complete accepted topology       | Reuses every accepted controller/stager tranche, but leaves the proof spread across system, controller, and runner workloads | Highest identity, TLS, token, IAM, RBAC, NetworkPolicy, storage, snapshot, audit, rendering, and teardown surface before first proof                | Rejected: topology preservation is not evidence that this is the shortest proof    |
| Reshape to serialized deployment | Reuses the API, service, real `Application`, handoff, listener, stop, retention, scheduler policy, and UID-safe cleanup      | One active run, one native controller host, one separate runner process, and one dedicated synthetic cluster reduce concurrent state and fixed cost | **Selected**                                                                       |
| Preserve and build a replacement | Keeps accepted code as an oracle but creates two implementations and two deployment truths                                   | Duplicates contract conformance, recovery, disclosure, cleanup, and acceptance work; longest route to exact evidence                                | Rejected: duplication adds drift without removing a product requirement            |
| Retire hosted proof              | Leaves the verified local beta coherent and removes all live abuse and spend                                                 | Lowest operational risk and cost, but provides no visitor-accessible process-loss proof or product-comprehension surface                            | Rejected for this one finite cycle; remains the deletion outcome if KAP-0070 stops |

Reshape has the shortest credible path because it removes deployment-only coordination while
preserving the already deep service and runner boundary. It does not infer safety from lower line
count. It replaces each removed control with a smaller control and requires fresh evidence.

## Historically selected serialized topology

KAP-0069 selected the following topology for KAP-0070 to prove. KAP-0070 later closed through
fallback, and KAP-0073 cancelled this topology:

```text
same-origin edge or reverse proxy
  -> one native controller host
       -> owner-private durable admission/receipt state
       -> durable global stop, serial scheduler, retention, and cleanup
       -> separate per-run native runner process and owner-private journal
            -> fixed conditional Application operation
                 -> one dedicated synthetic Kubernetes cluster
                      -> one policy-complete namespace and target at a time
```

At most one run may hold active execution or cleanup capacity. New work cannot dispatch until the
previous run's complete recorded UID/owner inventory is absent. The public queue remains bounded and
saturation still fails before admission. Serialization removed simultaneous visitor runs; it did not
remove adversarial isolation obligations. The cancelled route would have had to prove that the
active runner could not read controller state, receipts, keys outside its fixed inputs, prior-run
journals, an operator-owned isolation canary, or unrelated cluster resources.

The controller host and the synthetic cluster remain separately authorized resources. The host uses
one owner-private durable volume and one writer for admission and immutable receipt state. Each
runner executes under a separate least-privilege OS identity with one owner-private journal/outbox
and fixed read-only composition inputs. The existing authenticated private handoff remains the sole
runner-to-system report path. Scheduler and cleanup call their concrete service transitions locally;
they do not use the superseded remote controller-state protocols.

The cluster contains no controller database, receipt store, signing store, customer workload, or
production credential. It keeps a policy-complete namespace, fixed images, a sandboxed runtime or
equivalent independently proved boundary, enforced network policy, exact conditional patch
admission, separate target/runner/cleanup Kubernetes authority, immutable object identity, and UID-
safe deletion. No provider or product selection occurred; the planned pre-authorization fixture is
cancelled.

## Residual risk

A single controller host reduces deployment coordination but concentrates admission, receipt,
cleanup, Kubernetes controller credentials, and staged signing inputs in one security and
availability boundary. OS process isolation is weaker than independently enforced workload
identities, serialization reduces availability, and a dedicated cluster still retains runtime,
network, provider, cleanup, and cost risk. None was accepted live; KAP-0073 completed deletion
rather than another topology expansion.
