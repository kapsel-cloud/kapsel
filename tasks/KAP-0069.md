# Select The Bounded Public Product-Proof Route

Status: active decision packet. An explicit maintainer product-scope decision on 2026-07-30
authorizes route analysis that may select continuation, replacement, or retirement. This packet does
not authorize provider credentials, resources, spend, image push, endpoint, DNS, or public traffic.

Problem: the accepted sandbox contracts, implementation, fixtures, architecture review, and offline
deployment tranches contain substantial product and security evidence, but the paused deployment
route has not passed live acceptance. The `kapsel-sandbox` package also contains more than half of
the repository's Rust lines. Continuing its topology from sunk cost or replacing it from line count
would both be unsound. One finite decision must determine whether a hosted proof should continue
and, if so, select the smallest deployment route that preserves the properties required for a real
fixed-input crash-recovery proof.

Contract owners: [public sandbox API](../docs/SANDBOX_API.md),
[sandbox deployment](../docs/SANDBOX_DEPLOYMENT.md), [architecture](../docs/ARCHITECTURE.md),
[threat model](../docs/THREAT_MODEL.md), [privacy boundary](../docs/PRIVACY.md), and
[V1 technical direction](../docs/VISION.md).

Depends on: verified v0.2.0 publication, accepted KAP-0051, KAP-0052, KAP-0055, and KAP-0056
evidence, and only KAP-0053's accepted offline tranches. This packet replaces the previous
conditional wait for a sandbox decision; it does not make any earlier provider fixture or acceptance
an execution authority.

## Required product proof

Any continuation route must eventually let a visitor choose one fixed non-consequential scenario,
start one durable run, survive an intentional process-loss boundary, reconnect to the same
operation, observe no blind second mutation, inspect the real bounded result and receipt, and see
cleanup separately. The retire route instead terminates the hosted-proof route and creates no
deployment successor.

The caller supplies no arbitrary namespace, Deployment, image, grant, credential, manifest, shell,
text, lifecycle authority, or customer data. The proof is not a hosted customer product, production
environment, generic control plane, or compliance system.

## Decision boundary

This packet must choose the route; it must not become the route. Its complete output is:

1. one selected route;
2. one accepted decision record;
3. at most one follow-up implementation packet, and only for continuation; and
4. explicit closure or supersession of every unselected route.

No broad refactoring, new abstraction, or implementation belongs here. A decision-local probe is
allowed only when its result can invalidate one of the four routes.

## Decision work

1. Inventory the exact accepted sandbox contracts, implementation tranches, tests, deployment
   evidence, and unresolved live risks.
2. Separate product-essential properties from topology-specific implementation:
   - durable run identity and reconnect;
   - fixed scenarios and server-owned authority;
   - one conditional mutation opportunity through the real `Application`;
   - process-loss recovery and real receipt retrieval;
   - admission, rate, capacity, and cost bounds;
   - global stop;
   - run isolation and locator secrecy;
   - cleanup, retention, restart, rollback, and disclosure controls; and
   - ordered public projection with explicit receiver uncertainty.
3. Compare exactly four finite routes:
   - complete the accepted deployment topology;
   - reshape it into a simpler serialized deployment while preserving required properties;
   - preserve the accepted implementation and build a separately owned replacement; or
   - retire the hosted proof.
4. For every proposed simplification, name the security, isolation, custody, cleanup, acceptance, or
   operational property retained, replaced, weakened, or deleted. Line count is not evidence.
5. Classify accepted KAP-0051, KAP-0052, KAP-0055, KAP-0056, and each accepted KAP-0053 offline
   tranche as directly reusable, contractually reusable with new live evidence, superseded, or
   historical only.
6. Select one route using implementation locality, deployment complexity, public risk, operating
   cost, reproducibility, time to acceptance, and deletion tests.
7. For a continuation route, define one smallest standalone follow-up packet with exact contract
   owners, dependencies, authorization gates, validation, rollback, and residual risks. For retire,
   create no deployment follow-up and name the preservation or deletion work needed to leave a
   coherent terminal state.
8. Update the task route and downstream consumer blockers so old and selected deployment paths
   cannot appear simultaneously active. A retire decision must leave no implied live successor.

## Acceptance

- One explicit decision selects complete, reshape, preserve-and-replace, or retire.
- The decision record contains no implementation beyond a route-invalidating probe, creates at most
  one follow-up packet, and closes or supersedes every unselected route.
- The selected route has one finite objective and a deletion test.
- Existing accepted evidence is mapped individually rather than silently inherited or discarded.
- Superseded topology and gates are marked clearly.
- A continuation selection creates one packet naming exact isolation, disclosure, restart, cleanup,
  retention, saturation, cost, rollback, and stop-control evidence required before any live
  authorization request; a retire selection creates no deployment packet and marks downstream live
  routes terminal unless a later explicit direction reopens them.
- The root release package still builds after deleting the sandbox and no reverse dependency
  appears.
- Focused sandbox preservation gates and the repository docs gate pass.
- A fresh read-only architecture/security review finds no missing property or implicit provider
  authorization.

## Non-goals

No implementation beyond decision-local probes, automatic deployment, provider selection, spend,
credentials, endpoint, DNS, public traffic, resident service, second capability, generic hosted
platform, generic provider/storage/transport interface, or refactor justified only by physical line
count.

## Next action

Perform the inventory and route comparison, then select one route. Create one finite standalone
follow-up owner only for a continuation route; for retire, close the live route coherently without a
deployment successor. Do not begin deployment or broad refactoring inside this packet.

## Residual risk

The decision can still overvalue sunk implementation or oversimplify hard-won controls. Live
isolation, custody, cleanup, restart, rollback, saturation, cost, and reproducibility remain
unproved until the selected follow-up passes exact deployment acceptance.
