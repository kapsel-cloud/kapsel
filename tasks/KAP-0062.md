# Produce The v0.2 Beta Distribution Candidate

Status: queued after [KAP-0061](KAP-0061.md).

Problem: `v0.1.1` proves reproducible archive assembly but relies on an unauthenticated adjacent
checksum and carries experiment-era installation documentation. v0.2 needs one exact, authenticated,
reproducible beta candidate with upgrade, rollback, uninstall, SBOM, and downloaded-artifact proof.

Contract owners: [v0.2 release design](../docs/V0.2.md), [release artifacts](../docs/RELEASE.md),
[build](../docs/BUILD.md), [security policy](../SECURITY.md), and [privacy](../docs/PRIVACY.md).

Depends on: accepted KAP-0061 qualification manifest, baseline revision, permitted candidate deltas,
and exact budgets.

## Work

- Reconcile every change from the KAP-0061 baseline against its permitted-delta manifest. Any
  gateway, Application, CLI/MCP behavior, migration, or other executable-logic change returns to the
  narrowest owning packet before a new qualification baseline.
- Apply the one candidate version transition consistently across Cargo metadata, executable-reported
  versions, MCP server identity, archive name/layout, release metadata, changelog, and
  documentation; the shared workspace version does not distribute or support unpublished packages.
- Update the release contract for the exact v0.2 archive, metadata, bounds, checksum, and chosen
  publisher-authentication/provenance mechanism.
- Select, document, and test signing or attestation identity, verification, expiry, rotation,
  compromise, and replacement behavior; do not imply builder trust from a signature alone.
- Generate an SBOM bound to the exact archive, binaries, source revision, target, and relevant build
  inputs; record scanner/database identity and freshness.
- Package compatibility, upgrade, rollback/downgrade, security, evaluator, cleanup, and uninstall
  documentation.
- Assemble twice in isolated pinned environments and require byte-identical archives and sidecars
  where their formats permit determinism.
- Run only extracted files in a clean x86-64 GNU/Linux environment, including `v0.1.1` upgrade,
  CLI/MCP parity, restart, inspection, demo, cleanup, and uninstall.
- Rerun every KAP-0061 deterministic, fuzz, simulation, subprocess, live-kind, performance, privacy,
  and security gate affected by the candidate delta; bind the results to the exact candidate
  revision and artifact digests.
- Keep crates.io, docs.rs, source-package distribution, sandbox, credentials, journals, receipts,
  and private paths out of the release unit.

## Acceptance

- One exact candidate revision produces the named archive and sidecars with verified internal and
  external identity.
- Cargo, executable, MCP, archive, metadata, changelog, and documentation versions agree; no
  unpublished workspace package is presented as a distributed or supported artifact.
- The KAP-0061 manifest is reconciled against the candidate diff, and all affected qualification
  gates pass on the exact candidate rather than only on the earlier baseline.
- Safe extraction rejects unexpected entries, links, special files, unsafe modes, and size excess.
- Publisher authentication and provenance verification have explicit trust and failure procedures.
- SBOM and vulnerability review are bound to the candidate and have no unresolved release blocker.
- Two isolated assemblies satisfy the adopted reproducibility claim.
- A clean supported host completes install, `v0.1.1` upgrade, operation/restart, MCP, inspection,
  disposable-kind demonstration, rollback procedure, cleanup, and uninstall from downloaded files.
- Current docs state every supported and unsupported beta surface and residual risk.
- Fresh supply-chain, security, compatibility, release, and privacy reviews find no blocker.

## Non-goals

No publication, tag, crates.io upload, second target, production support, hosted endpoint, sandbox
image, crate or package-module extraction, or website claim before acceptance.

## Next action

Freeze the exact release candidate inputs and evidence, then hand them to [KAP-0063](KAP-0063.md).
Any executable correction returns to the narrowest owning packet and creates a new candidate
revision.

## Residual risk

Publisher authentication identifies an approved release act; it does not prove source review,
builder integrity, dependency safety, or operational fitness. Those claims remain bounded by their
separate evidence.
