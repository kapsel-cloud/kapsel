# Produce The v0.2 Beta Distribution Candidate

Status: complete historical candidate. Exact commit `450a0d5e5f6c1f6f046fba51979ea6a18539544c`
passed qualification and artifact verification but was superseded unchanged by KAP-0065's

## Frozen candidate design

The candidate version is `0.2.0`; the sole target remains `x86_64-unknown-linux-gnu`. The root
`kapsel` archive is the only distributed package. The inherited workspace version on unpublished
`kapsel-dev` and `kapsel-sandbox` packages is build metadata, not a distribution or support claim.

One clean assembly emits four deterministic files with the archive basename as their common prefix:

```text
kapsel-0.2.0-x86_64-unknown-linux-gnu.tar.gz
kapsel-0.2.0-x86_64-unknown-linux-gnu.tar.gz.sha256
kapsel-0.2.0-x86_64-unknown-linux-gnu.tar.gz.spdx.json
kapsel-0.2.0-x86_64-unknown-linux-gnu.tar.gz.SHA256SUMS
```

The checksum identifies the archive bytes. The SPDX 2.3 JSON sidecar identifies the archive, bundled
binaries, exact source revision/tree, target, builder input, Cargo lockfile, and complete locked
Rust dependency graph used by the root package. Its `created` field is normalized to the source
commit time for reproducibility. `SHA256SUMS` is the lexically ordered, basename-only digest
manifest for the archive, checksum, and SBOM.

One maintainer-dispatched GitHub Actions workflow at the exact candidate revision uses Cosign
`v3.1.2` keyless blob signing to sign `SHA256SUMS`. It emits one Sigstore bundle named by appending
`.sigstore.json`. The appointed publisher identity is the exact
`kapsel-cloud/kapsel/.github/workflows/release-candidate.yml@refs/heads/master` GitHub workflow
under issuer `https://token.actions.githubusercontent.com`; verification additionally requires the
exact repository, ref, source revision, workflow trigger, and candidate manifest bytes. The bundle
is an external event record and is intentionally nondeterministic. It is excluded from
byte-reproducible assembly while its exact digest and successful semantic verification are retained
as candidate evidence.

Connected verification refreshes Sigstore trust through its TUF root. Offline verification uses an
explicitly captured trusted-root snapshot and cannot discover later rotation, compromise,
withdrawal, or replacement. Fulcio certificate expiry is evaluated against authenticated bundle
time, not wall-clock time alone. There is no long-lived Kapsel signing key. Suspected repository,
workflow, issuer, Fulcio, Rekor, or candidate compromise disables the workflow, withdraws the exact
candidate digests, and produces a newly named candidate and bundle; files are never overwritten or
silently re-signed in place. Release verification requires connected re-verification of the exact
published bytes.

The archive retains the existing binary and demonstration layout and additionally bundles
`COMMANDS.md`, `MCP.md`, `RELEASE.md`, `UPGRADE.md`, `SECURITY.md`, and `PRIVACY.md` beside the
evaluator guide. Metadata schema v2 binds source tree, lockfile, binary sizes/digests, fixed build
and smoke images, and the developer-beta non-claims. The compressed, expanded, and per-file archive
bounds remain 32 MiB, 64 MiB, and 32 MiB. The checksum, SBOM, digest manifest, and Sigstore bundle
are bounded to 256 bytes, 2 MiB, 1 KiB, and 1 MiB respectively.

The `0.2.0` transition changes Cargo identity, ordinary executable `--version` behavior, MCP
`serverInfo.version`, and binary digests. It therefore triggers every KAP-0061 lane. Distribution
documentation, schema, SBOM, signing workflow, and artifact-only automation separately trigger the
default, privacy, Trivy, and their owned distribution lanes. No planned delta changes KAP-0038
semantics, security policy, qualification budgets, dependencies, toolchain, feature composition, or
supported compatibility meaning; any such discovered change returns to its direct owner.

- One exact candidate revision produces the named archive and sidecars with verified internal and
  external identity.
- Cargo, executable, MCP, archive, metadata, changelog, and documentation versions agree; no
  unpublished workspace package is presented as a distributed or supported artifact.
- The KAP-0061 manifest is reconciled against the candidate diff, and all affected qualification
  gates pass on the exact candidate rather than only on the earlier baseline.
- Safe extraction rejects unexpected entries, links, special files, unsafe modes, and size excess.
- Publisher authentication and provenance verification have explicit trust and failure procedures.
- SBOM and vulnerability review are bound to the candidate and have no unresolved release blocker.
- Two isolated assemblies satisfy the adopted reproducibility claim.
- A clean supported host completes install, `v0.1.1` upgrade, operation/restart, MCP, inspection,
  disposable-kind demonstration, rollback procedure, cleanup, and uninstall from downloaded files.
- Current docs state every supported and unsupported beta surface and residual risk.
- Fresh supply-chain, security, compatibility, release, and privacy reviews find no blocker.

## Non-goals

No publication, tag, crates.io upload, second target, production support, hosted endpoint, sandbox
image, crate or package-module extraction, or unsupported public claim before acceptance.

## Residual risk

Publisher authentication identifies an approved release act; it does not prove source review,
builder integrity, dependency safety, or operational fitness. Those claims remain bounded by their
separate evidence.
