# Prove v0.1.1 Upgrade And Rollback

Status: complete and independently reviewed. Exact tagged-source `v0.1.1` journals now cross the
accepted backup, marker, restore, rollback, and downgrade procedure without changed lifecycle or
receipt facts.

Problem: a developer beta cannot safely replace `v0.1.1` if opening existing durable state may lose
operation identity, repeat a mutation, re-sign frozen receipt bytes, or leave an operator unable to
restore or diagnose a failed upgrade. Internal SQL remains private, but operational continuity must
be explicit.

Contract owners: [v0.2 release design](../docs/V0.2.md), KAP-0038, and
[testing](../docs/TESTING.md). This packet must create `docs/UPGRADE.md` as the canonical
operational upgrade, backup, restore, rollback, and downgrade contract; the journal implementation
remains private evidence, not an owner.

Depends on: adopted KAP-0059 types, vectors, and compatibility classes.

## Work

- Produce exact `v0.1.1` journal fixtures at every durable lifecycle state from accepted release
  behavior, not hand-written approximations.
- Define the candidate schema/version marker, backup, atomic migration, reopen, restore, and cleanup
  rules without exposing SQL as a public interface.
- Test crash before, during, and after migration plus idempotent reopen.
- Preserve requested, authorized, not-attempted, apply-started, receiver-observed, receipt-prepared,
  receipt-written, and finalized operations.
- Preserve provider call count, target/receiver facts, receipt bytes/path/digest/key identity, and
  retained v2 inspection.
- Select and document whether the old binary can reopen migrated state; if not, prove bounded,
  non-destructive downgrade refusal and exact restore instructions.
- Create `docs/UPGRADE.md` as the direct owner for the accepted operator procedure and keep SQL,
  schema details, and test-fixture construction private.
- Cross migration and rollback with real subprocess loss rather than only in-process errors.

## Acceptance

- Every matrix case names old/new binary, initial state, crash point, expected durable state,
  provider call count, receipt identity, backup fact, and allowed operator action.
- No migration case can issue a blind second mutation after `apply_started`.
- Frozen receipts are never re-signed, relocated, or reclassified.
- Backup/restore is integrity-checked, owner-private, restart-safe, and leaves no ambiguous active
  store.
- Failed migration and unsupported downgrade are bounded and non-destructive.
- Exact retained grant v1 and receipt v2 vectors remain accepted as owned by KAP-0038 and exposed
  through the KAP-0059 compatibility surfaces.
- `docs/UPGRADE.md` states the complete supported procedure, failure modes, rollback/downgrade
  policy, and non-claims without exposing internal SQL.
- Focused migration/subprocess tests, simulation, default gate, and fresh lifecycle, storage,
  compatibility, and recovery review pass.

## Non-goals

No generic migration framework, storage interface, distributed journal, SQL compatibility promise,
new capability, performance qualification, packaging, version tag, or publication.

## Evidence

- The annotated `v0.1.1` tag object and peeled release commit are pinned before a detached
  historical worktree generates all eight durable states plus both zero-call and one-call
  `apply_started` realities through accepted tagged lifecycle behavior rather than handwritten rows.
- `docs/UPGRADE.md` owns one stopped-process, owner-private raw backup and digest procedure, two
  migration-only MCP clean-EOF opens, bounded failures, atomic still-present-path restore,
  quarantine, direct exact-`v0.1.1` downgrade, cleanup, and non-claims. No command grammar or public
  SQL promise changed.
- Existing unmarked stores require byte-identical owner-private backup evidence before one exclusive
  SQLite transaction records private marker 2. Exact `v0.1.1` rows require no transformation.
  Unknown versions, unsafe paths/links/modes, WAL, malformed layouts, and mismatched backups refuse
  without marking the source.
- Complete layout recognition covers the owned schema, ordinary and hidden column facts, STRICT
  status, the implicit primary-key index, and absence of extra tables, views, triggers, or indexes.
  Rollback-journal `DELETE` and `synchronous=FULL` are configured and verified before any marker or
  legacy-maintenance write.
- The provenance-bound gate crosses nine fixtures at three real candidate migration-loss seams and
  three private restore-loss seams: 54 killed processes. Every case performs ordinary reopen and
  compares the complete operation row, provider-call count, backup identity and bytes, frozen
  receipt path/bytes/digest/key/publication, and complete retained-v2 inspection. The exact tagged
  old opener then leaves each marked database byte-identical.
- The hot-rollback recovery branch is separately exercised with a `cfg(test)`-only controlled
  marker-page write while a nonzero hot journal owns the old page; recovery proves marker 0, exact
  schema and row, absent probe, and no residual rollback journal before normal re-mark. This is not
  presented as natural production page spilling.
- Corrupted backup/digest and hostile restore artifact shapes are non-destructive. Accepted files
  remain owner-private and singly linked; tests reject symlink, dangling-symlink, hardlink,
  permissive, and wrong-type replacement or quarantine entries and reject the fixed signing seed in
  retained files.
- `cargo make test-v011-upgrade`, focused migration/lifecycle/vector/package tests, the seeded
  1,000-case simulation, Clippy, formatting, links, diff hygiene, and the complete default gate
  passed. Fresh lifecycle/recovery, SQLite/filesystem, compatibility, and operator-documentation
  reviews closed all findings.

## Residual risk

The evidence uses source-built local processes, not the downloaded x86-64 GNU/Linux release
artifact. Process termination does not prove sudden power loss, torn sectors, dishonest flushes,
controller-cache durability, or filesystems that violate SQLite, atomic-rename, file-sync, or
parent-directory-sync guarantees. The later downloaded-artifact lane must repeat representative
upgrades with exact published binaries.
