# Qualify The v0.2 Beta

Status: complete. The original independently accepted native-Linux baseline was bound to measured
source commit `c75f196a06993e9c1681e51004f19497fb7a1bb4` and committed in `9772f94`. KAP-0062 reran
the closed orchestrator on its exact distribution candidate. KAP-0065 reran it again for the
documentation-corrected replacement; the tracked manifest is bound to
`5fe0407cd5ebd78f386905e33f79e0f712a57835`.

Problem: clean architecture and migration proof do not establish bounded behavior under hostile
input, repeated recovery, supported-environment variance, dependency failure, or resource pressure.
The beta needs finite measured stopping rules rather than a broad production-readiness program.

Contract owners: [v0.2 release design](../docs/V0.2.md), [testing](../docs/TESTING.md),
[threat model](../docs/THREAT_MODEL.md), [security policy](../SECURITY.md), and KAP-0038.

Depends on: one lifecycle implementation, adopted beta interfaces, accepted migration behavior, and
accepted root release-source locality.

## Frozen qualification design

This design is fixed before KAP-0061 measurement. Budgets are finite candidate stopping rules, not
public latency, throughput, availability, production, or support promises.

### Scope and environments

- Qualify only the root `kapsel` package, ordinary executable, fixed stdio MCP adapter, exact grant
  and receipt compatibility, private journal upgrade/recovery, the compile-time demonstration
  executable, and the sole concrete Kubernetes adapter. Exclude `kapsel-sandbox`, release assembly,
  publisher authentication, SBOM production, packaging, and publication.
- Run every lane on the dedicated native x86-64 Linux qualification host. Run supported-target
  resource measurements in the pinned
  `rust@sha256:a339861ae23e9abb272cea45dfafde21760d2ce6577a70f8a926153677902663` Debian 12
  `linux/amd64` container used by release assembly, with 8 CPUs and 8 GiB available. The host
  reports no hypervisor or container virtualization; the measurement environment is nevertheless an
  isolated Docker container and is not evidence of uncontainerized or production performance.
- Run live semantics only against the uniquely named disposable kind cluster, kind v0.32 or newer,
  kubectl v1.30 or newer, and pinned Kubernetes v1.33 node image already owned by `docs/BUILD.md`.
  Cluster creation/image loading time is recorded separately from Kapsel scenario time.
- Before the first sample, freeze the host tool identities as Rust 1.96.1 commit
  `31fca3adb283cc9dfd56b49cdee9a96eb9c96ffd`, Cargo 1.96.1, Python 3.13.5, Docker client/server
  29.5.2, kind 0.32.0, kubectl 1.33.9, cargo-fuzz 0.13.1, nightly Rust commit
  `c397dae808f70caebab1fc4e11b3edf7e59f58c7`, cargo-audit 0.22.2, and Trivy 0.72.0. The pinned
  container supplies x86-64 Rust/Cargo 1.96.1 and Python 3.11.2. The initially predeclared
  cargo-audit 0.21.2 became unable to parse the freshly updated RustSec database after it introduced
  CVSS 4.0 advisories; qualification therefore stops that attempted lane and explicitly adopts
  0.22.2 before the accepted scan. A changed identity invalidates its affected lane rather than
  being silently accepted.
- Record exact host/container OS, architecture, CPU count, memory, Rust/Cargo/Python, Docker, kind,
  kubectl, cargo-fuzz, scanner version/database timestamp, source revision, source-tree digest, and
  executable digest with every applicable result.

### Samples, failure ceilings, and statistics

- Every correctness, security, hostile-input, subprocess, fuzz, simulation, demo, and live-kind lane
  permits zero assertion failures, crashes, leaked owned resources, unexpected provider calls,
  changed frozen bytes, or findings rejected by the frozen security policy below. This packet does
  not invent a separate sanitizer claim.
- Receipt inspection fuzzing runs exactly 10,000 cases with libFuzzer seed `2118243591`, cargo-fuzz
  0.13.1, the frozen nightly commit above, and only the canonical corpus file whose pre-run SHA-256
  is `86dda67e958b96cd56452de77199c2ebfac36400d6c971e84966a4b9fb3e9e8d`. The temporary corpus is
  sorted and contains no generated carry-over inputs. On failure the output must name the artifact,
  libFuzzer seed, and exact replay command; successful input bytes are not printed.
- The seeded lifecycle simulation runs exactly 10,000 cases with seed `21182435914953528`; its
  failure output names seed and case. Fuzz and simulation must each complete within 10 minutes.
- Deterministic process matrices cross every existing mutation, receipt-publication, migration, and
  restore seam. Live kind runs one healthy, one `ProgressDeadlineExceeded`, and one bounded
  `UNKNOWN` scenario with owned cleanup.
- Local phase measurements discard five warmups and retain 30 samples for every repeatable class
  named below. Use nearest-rank p95 for phase latency and CPU; use the maximum for startup, bounded
  observation, peak RSS, sizes, growth, live scenario time, and cleanup. Any failed sample fails the
  budget rather than disappearing from the denominator.

### Frozen workloads and measurement boundaries

One private, ignored, release-optimized Rust qualification test measures internal phases through the
existing Journal/Gateway and concrete-adapter test seams; it adds no production interface. One
Python 3.11 harness runs that test and the ordinary release executable inside the pinned x86-64
container, validates JSON output, computes integer nearest-rank statistics, and writes only bounded
results. The following IDs and classes are fixed:

- `process_startup`: execute the stripped ordinary `kapsel` binary with no arguments; measure from
  direct-child spawn immediately through its bounded usage exit. It receives no files or stdin.
- `grant_provision`: provision the fixed maximal-valid exact authorization from one owner-private
  JSON file and 32-byte seed to a new output pathname. Per-sample setup and cleanup are outside the
  interval.
- `journal_fresh_open` and `journal_marked_open`: execute `kapsel mcp --operator-config FIXED` with
  closed stdin against respectively a new empty journal and its immediately reopened marker-2
  journal. Fixed owner-private configuration and loopback endpoint setup are outside the interval;
  no MCP frame or lifecycle work occurs.
- `offline_inspection`: execute `kapsel inspect` over the canonical receipt/trust v2 files at
  explicit evaluation time 150. File setup and output validation are outside the interval.
- `submit_authorized`: time one new maximal-valid request from absent row through durable
  `authorized`, including exact grant verification but no provider call.
- `target_read` and `conditional_patch`: time the concrete adapter’s safe GET and one conditional
  strategic patch separately against a deterministic loopback Kubernetes fixture. Fixture startup
  and response delay are zero and excluded; request parsing and response validation remain inside.
- `reconcile_apply_started`: begin with the exact request durably at `apply_started`, reopen,
  observe matching receiver facts through the deterministic adapter, require zero patch calls, and
  stop at `receiver_observed`.
- `receipt_finalize`: begin at `receiver_observed` and time construction, signing, owner-private
  no-replace publication, and finalization of exact bytes.
- `restart_recovery`: first create `apply_started` with one returned patch and kill/fault before
  outcome persistence outside the interval; then time reopen plus observation to
  `receiver_observed`, requiring no second patch.
- `complete_success`: time one ordinary `kapsel operate` process from spawn against a fresh journal
  and deterministic successful loopback fixture through target read, one patch, receiver
  observation, receipt construction/publication/finalization, machine output, and process exit.
- `complete_recovery`: outside the interval, use the demonstration binary and owned marker to create
  exactly one returned patch and kill it at `after_apply`; then time one ordinary `kapsel operate`
  process from spawn through restart-only observation, receipt finalization, machine output, and
  exit, requiring the fixture patch count to remain one. Both complete classes use five warmups and
  30 retained samples.
- `bounded_unknown_observation`: one non-repeatable maximum sample uses the production 30-read,
  one-second schedule against a deterministic 404 fixture and requires `UNKNOWN`. The live unknown
  scenario independently patches once, stops after `ApplyReturned`, deletes that exact Deployment,
  restarts with a zero-patch counting adapter, exhausts the same 30-read schedule, freezes and
  inspects an `UNKNOWN` receipt, and removes only its owned namespace.

The Python wrapper uses `time.monotonic_ns()` for wall time and a fresh wrapper process using
`resource.getrusage(RUSAGE_CHILDREN)` for direct-child user+system CPU and maximum RSS. Kapsel
spawns no child process; fixture server resources are measured separately and excluded. CPU is
reported in microseconds, wall time in microseconds, RSS in bytes, and sizes in bytes. Process
setup, input-file creation, fixture readiness, output validation, and cleanup are outside command
intervals and are reported separately.

Journal growth uses one fresh marker-2 database, then 10,000 distinct requested rows whose request
fields are maximal-valid values. After a clean close it requires no rollback/WAL/SHM sidecar and
records main-file `st_size`, SQLite `page_count * page_size`, empty-store size, and
`(final_size - empty_size) / 10000`; allocated-block size is not the budget. Receipt size uses one
maximal-valid classifier-complete generated receipt plus the canonical v2 files. Executables are
built with the pinned image using
`cargo build --release --locked --target x86_64-unknown-linux-gnu`, once ordinary and once with
`--features demo-harness`; the existing release profile’s `strip = true` is the sole stripping step,
and ELF inspection must report stripped x86-64 binaries.

### Frozen security policy

- Refresh the RustSec and Trivy vulnerability databases immediately before scanning; record database
  identity/time and fail if unavailable or older than 24 hours. The stopped cargo-audit 0.21.2
  attempt is retained only as correction evidence; the accepted scan uses exact cargo-audit 0.22.2.
- `cargo audit --json` through exact cargo-audit 0.22.2 covers the locked workspace dependency graph
  and rejects every RustSec vulnerability. Yanked, unmaintained, or unsound warnings are findings
  requiring disposition.
- Trivy 0.72.0 scans the repository filesystem/lockfiles for vulnerabilities and secrets. Any
  detected `HIGH` or `CRITICAL` vulnerability, verified secret, or scanner error fails. Lower
  severities remain recorded for review rather than silently discarded.
- An exception requires reachability analysis, threat-owner approval, compensating control, named
  owner, and expiry no later than 30 days or KAP-0063 acceptance, whichever comes first. No
  exception is permitted for a reachable high/critical issue, exposed credential, false receiver
  result, blind retry, signature/trust bypass, unsafe path replacement, or unbounded production
  input.
- Dependency, key/trust, filesystem, disclosure, privacy, and no-SLA review uses the same baseline.
  Complete vulnerability absence, malicious-package absence, and future database knowledge remain
  explicit non-claims.

### Evidence and candidate reconciliation

The packet produces one tracked `qualification/kap0061-baseline.json` manifest with
`schema_version: 1`. A standard-library validator owns its exact closed field sets and types:

- lowercase SHA-1 commits/tree identities and lowercase SHA-256 source, executable, input, database,
  and bounded-output digests;
- a baseline object naming the clean measured parent commit, Git tree, and a canonical source digest
  over sorted NUL-delimited `path\0blob-bytes\0` records for `Cargo.toml`, `Cargo.lock`,
  `rust-toolchain.toml`, `Makefile.toml`, `src/**`, and `vectors/**` at that commit;
- environment and tool arrays with stable IDs, exact version strings, architecture, integer CPU and
  byte memory values, virtualization fact, and optional database UTC timestamp;
- budget objects with stable ID, metric, class, statistic (`p95` or `maximum`), integer limit,
  comparator, unit, warmups, required samples, and failure ceiling;
- exactly one result per frozen lane and complete frozen budget, with stable ID, environment ID,
  command argv, sorted input SHA-256 map, status (`passed`, `failed`, or `not_applicable`), integer
  sample/failure counts, duration in milliseconds, bounded-output SHA-256, exactly one budget-linked
  integer measurement with matching statistic/unit/limit, and nonempty assertion facts.
  `not_applicable` requires a reason and owner; no required KAP-0061 lane may use it;
- security findings/exceptions, review dispositions, residual risks, and KAP-0062 invalidation rules
  as closed typed objects. Null, unknown fields, duplicate IDs, floats, absolute private paths,
  credentials, journals, receipt bytes, signing-key material, and raw provider bodies are rejected;
  numeric fuzz/simulation replay seeds remain required.

The validator freezes the 43 complete budget definitions, 11 required lanes, replay seeds/counts,
closed privacy command, required semantic assertion IDs, producer/input links, and invalidation lane
sets. It rejects deletion of a budget and its result together, count/statistic/unit/limit mismatch,
changed replay identity, disconnected live or measurement evidence, placeholder privacy commands,
and duplicate or incomplete invalidation lanes.

Raw bounded outputs remain temporary; the manifest stores their SHA-256 and non-sensitive aggregate
facts. The measured baseline commit precedes the final manifest/evidence commit. The manifest path
and later task/routing text are excluded from the canonical source digest, while the explicit parent
commit and Git tree bind their historical inputs. This is qualification-baseline evidence, never
release-candidate evidence.

KAP-0062 may add distribution documentation, release metadata, authenticated publication inputs,
SBOM/provenance sidecars, and artifact-only automation without reopening semantic design. Such
non-executable changes rerun formatting, links, privacy/security review, and their owned
distribution lanes. Changes to a qualification script, validator, test, fixture, vector, fuzz
corpus, simulation generator, live-kind/demo harness, measurement tool, scanner policy/database,
environment, or tool identity conservatively invalidate all KAP-0061 lanes even when executable
bytes are unchanged. Any root source, dependency, lockfile, toolchain, feature composition,
compatibility owner, command behavior, or executable digest change—including a version-identity
change—requires the complete default, hostile-input, fuzz, simulation, subprocess, live-kind,
performance/resource, dependency, privacy, and security lanes against the exact candidate. A
semantic, security-policy, or budget-changing delta returns to KAP-0061 rather than being waived by
KAP-0062.

  absolute paths, missing budget/lane results, non-lowercase digests, and nonpassing required
  evidence. Raw journals, provider bodies, receipt bytes, key material, and scanner output remain
  temporary and are represented only by bounded aggregates and SHA-256 digests.
- The measured parent commit and tree precede this task/manifest commit. The active

- KAP-0065 reran the complete closed orchestrator on native x86-64 Linux against exact replacement

## Final independent review

The 2026-07-28 final review accepted this packet with no blocker. It independently confirmed the
UTF-8 byte, atomic capacity, exact-mode, deterministic bounded-unknown, explicit-target, scanner,
source, executable, harness, environment, producer-command, budget, replay, and invalidation
bindings. Twenty-three targeted false-attestation mutations were rejected, and the focused
validator, privacy, orchestrator, storage, formatting, and diff-hygiene gates passed without
rerunning expensive qualification lanes.

The accepted residual risks remain the limits of one native host and one kind environment,
containerized rather than production performance, scanner knowledge, and beta-scoped storage and
lifecycle semantics.

## Acceptance

- All production hostile-input interfaces have bounded owner-specific proof and no unresolved
  release blocker.
- Every security, compatibility, and resource bound in the root v0.2 release behavior is named,
  enforced at runtime where externally influenced, and compile-time checked where related constants
  encode an internal invariant. Wire-format, adapter, and storage constants remain with their owners
  unless shared semantics are explicitly established; externally observable changes update their
  direct contract owners.
- Seeded simulation and subprocess matrices print exact replay inputs and preserve mutation/receipt
  invariants.
- Live-kind healthy, failed, and unknown paths preserve one-attempt and cleanup evidence.
- Every performance result records environment, revision, state/input class, sample/failure count,
  and selected percentile or maximum.
- Candidate budgets pass without becoming public production or latency promises.
- Security review records supported beta posture, no-SLA limits, dependency findings, exceptions,
  owners, and expiry.
- Default, fuzz, simulation, demo, and live-kind lanes plus fresh reliability, performance, privacy,
  and security review pass.
- One qualification manifest binds all evidence to the baseline revision and states that it is not
  release-candidate evidence until KAP-0062 reconciles and reruns it against the exact candidate.

must state that limit and avoid converting measured local behavior into universal support claims.
