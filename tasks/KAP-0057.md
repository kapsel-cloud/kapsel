# Define The Finite v0.2.0 Release Unit

Status: first design slice complete and accepted. [`docs/V0.2.md`](../docs/V0.2.md) now owns the
prospective finite release unit, surface inventory, unresolved decisions, and conditional gates;
fresh architecture, compatibility, security, and release review found no blocker. Implementation,
version changes, compatibility promotion, and publication remain blocked until KAP-0047 supplies
approved aggregate evidence and KAP-0046 explicitly selects the Stabilize route.

Problem: the workspace version covers the published root artifact and unpublished support packages,
while the CLI, MCP behavior, Rust interface, grant and receipt wires, SQL stores, sandbox HTTP
contract, private controller protocols, deployment manifests, and hosted endpoint have different
owners and maturity. Treating completion of the large KAP-0053 hosted proof as “v0.2.0,” or changing
the workspace version without naming the release unit, would silently turn experimental internals
into compatibility promises. Conversely, waiting for every optional hosted proof before designing a
bounded root release makes release quality depend on unrelated cloud scope.

Direct owners: [technical scope](../docs/SCOPE.md), [V1 technical direction](../docs/VISION.md),
[release process](../docs/RELEASE.md), [testing strategy](../docs/TESTING.md), completed
[KAP-0049 self-serve release](KAP-0049.md), evaluator evidence packet [KAP-0047](KAP-0047.md), and
direction decision [KAP-0046](KAP-0046.md).

Depends on: the published `v0.1.1` artifact for factual baseline. Final acceptance and any
implementation depend on sufficient approved aggregate KAP-0047 evidence plus KAP-0046 choosing
**Stabilize**. KAP-0050/KAP-0053 sandbox completion is not a prerequisite for this design packet or
for evaluating the local artifact. If a later release owner chooses to include a deployed sandbox
revision as release evidence, that dependency must be added explicitly rather than inferred.

## Decision boundary

This packet designs one possible stabilization release. It does not decide that Kapsel should ship
v0.2.0, change a version, widen scope, add a capability, or claim production readiness.

The proposed release unit starts from:

```text
published artifact: kapsel root binary/package
supporting evidence: exact source, vectors, tests, docs, release metadata
not distributed: kapsel-sandbox, kapsel-dev, fuzz, deployment credentials/resources
```

The design must reject the assumption that one Cargo workspace version stabilizes every package,
wire, database, fixture, deployment, or hosted interface.

## First design slice

Create one canonical prospective v0.2.0 release design that:

1. inventories every current artifact and externally observable surface;
2. classifies each as proposed compatible, versioned-but-experimental, operationally migratable but
   private, or explicitly unsupported/non-surface;
3. states that `kapsel-sandbox` remains unpublished hosted-proof implementation and is excluded from
   the distributed v0.2.0 release unit unless a later explicit owner changes that decision;
4. names the exact local artifact, supported platform proposal, installation form, CLI/MCP/Rust
   surfaces, grant/receipt vectors, journal behavior, and artifact layout that would require a
   compatibility decision;
5. defines the migration, downgrade, rollback, and retained-data questions that implementation must
   answer before release;
6. proposes reliability, performance, security, supply-chain, documentation, and independent-review
   gates with literal measurable outputs rather than a broad “production ready” goal;
7. records explicit non-goals and package-extraction triggers from VISION; and
8. identifies which choices require KAP-0047 evidence or the KAP-0046 stabilize decision instead of
   filling them with assumptions.

The design should live in one canonical owner under `docs/`, linked from `docs/INDEX.md`. It must be
prospective, clearly non-authorizing, and concise enough to review as a release contract rather than
a new product vision.

## Architecture and ownership rules

- `kapsel` remains the deep product package for the one concrete capability.
- `kapsel-sandbox -> kapsel` remains one-way; sandbox code does not move into the release package.
- `kapsel-dev` and `fuzz` remain repository tooling/evidence, not runtime dependencies.
- Do not create `kapseld`, receipt, protocol, client SDK, Kubernetes, storage, provider, or separate
  CLI packages unless the corresponding VISION trigger has independently passed.
- Do not split modules by line count. Refactor only measured defects or support hotspots and keep
  invariants with their owner.
- KAP-0038 grant matching, durable attempt/recovery semantics, receiver-bounded results, explicit
  `UNKNOWN`, and frozen receipt bytes remain unchanged unless a higher-authority owner explicitly
  opens them.

## Quality categories to design

### Compatibility

Name, do not assume, the policy for CLI commands/options/output, MCP initialization/tool behavior,
Rust exports, grant and receipt bytes, journal schema, artifact paths, configuration, and supported
platform. Internal SQL and private Rust modules remain non-public even when operational migration is
supported.

### Migration and rollback

Specify the required test matrix for `0.1.1 -> 0.2.0`, failed migration, restart at every durable
state, backup/restore, downgrade support or explicit refusal, rollback, and immutable receipt
inspection. No migration implementation belongs in the first design slice.

### Robustness and security

Define finite owner-specific proof for authorization, filesystem safety, Kubernetes behavior,
process loss, malformed input, dependency outage, key handling, receipt publication, and recovery.
Coverage percentage remains informational.

### Performance

Propose bounded measurements for local admission, target read/patch/observation, journal operations,
receipt publication/inspection, process restart, memory, CPU, and retained bytes. Do not publish
throughput or latency promises before measurements select defensible budgets.

### Distribution and supply chain

Decide what evidence would improve on adjacent checksums: clean assembly, reproducibility,
provenance/signing/attestation, SBOM, vulnerability review, downloaded-artifact verification,
install/uninstall, and live `kind` smoke on each supported target.

## Acceptance

- One prospective owner names the release unit and every candidate compatibility surface.
- Distributed root artifact and optional hosted sandbox evidence remain separate.
- Every unknown is assigned to KAP-0047 evidence, KAP-0046 decision, or a finite later
  implementation packet; none is silently resolved by wording.
- The design defines measurable quality gates without claiming production readiness.
- No code, Cargo version, wire version, schema, package, capability, provider seam, or release tag
  is changed.
- Fresh architecture, compatibility, security, and release reviews find no blocker in the design.
- If KAP-0046 does not choose Stabilize, this packet closes as unused design context and creates no
  implementation momentum.

## Non-goals

No automatic v0.2.0 release, second capability, daemon, hosted control plane, public sandbox
completion, provider deployment, compatibility promise, package extraction, market plan, pricing,
customer record, or production-readiness claim.

## Next action

Preserve the reviewed prospective design without creating implementation momentum. KAP-0047 may
continue the local `v0.1.1` evaluator evidence cycle without waiting for KAP-0050. Do not create
v0.2.0 implementation tasks or modify versions until KAP-0046 selects Stabilize and adopts or
corrects the reviewed design from evidence.

## Residual risk

A prospective design can overfit repository concerns before evaluator evidence exists. Explicit
unknowns and the KAP-0046 gate prevent the document from becoming an implicit roadmap. The local
artifact may ultimately warrant freeze, retirement, one evaluator-blocking `0.1.x` patch, or a
release shape different from this proposal.
