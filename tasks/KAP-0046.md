# Stabilize One Deep Kubernetes Effect-Gateway Beta

Status: complete direction decision. **Stabilize** is selected; implementation is authorized only
through the ordered v0.2 packets in [`docs/V0.2.md`](../docs/V0.2.md).

Problem: Kapsel's 0.1 releases prove the hard effect-gateway semantics, but requiring an independent
`v0.1.1` evaluator campaign before any further implementation turns a technical product bet into a
recruitment gate. Conversely, continuing architecture work without a finite release owner would
create an open-ended internal program.

Contract owners: [technical scope](../docs/SCOPE.md),
[KAP-0038](../docs/experiments/KAP-0038-kubernetes-effect-gateway-boundary.md),
[architecture](../docs/ARCHITECTURE.md), [v0.2 release design](../docs/V0.2.md), and
[ADR 0008](../docs/decisions/0008-use-one-kubernetes-effect-gateway-canary.md).

## Inputs

- The published and clean-room-verified `v0.1.1` artifact.
- Deterministic lifecycle, authorization, hostile-input, subprocess, MCP, artifact, reproducibility,
  and live-kind evidence already recorded by the 0.1 release packets.
- The reviewed finite release-unit inventory from [KAP-0057](KAP-0057.md).
- The current architecture review finding that the root product is deep but retains parallel
  lifecycle test paths, a wider-than-needed Rust surface, and duplicated CLI/MCP domain projection.
- An explicit maintainer decision to build and market a technology-led developer beta before using
  external adoption as the next direction gate.

No external-use, buyer, market, production-fitness, or commercial validation is claimed.

## Decision

Choose **Stabilize**.

Kapsel will build v0.2.0 as one finite Kubernetes effect-gateway developer beta around the existing
`kubernetes.set_deployment_image` capability. It will deepen the exact authorization, durable
attempt, crash recovery, receiver observation, explicit `UNKNOWN`, signed receipt, CLI, MCP, and
artifact path without adding another capability or generic provider interface.

The accepted [`docs/V0.2.md`](../docs/V0.2.md) release design owns the product promise,
compatibility classes, package exclusions, ordered implementation packets, acceptance proof, and
website handoff.

External evidence moves after publication. [KAP-0047](KAP-0047.md) will evaluate the exact beta
artifact and inform what follows; it no longer blocks v0.2 implementation.

## Rejected alternatives

- **Specify one capability:** rejected for v0.2 because widening before the first complete beta
  would multiply authorization, retry, receiver, and receipt semantics and reduce module depth.
- **Freeze:** rejected because the existing proof has enough technical substance to justify one
  bounded product-quality release cycle.
- **Retire:** rejected because the effect-gateway proposition remains technically differentiated and
  can be tested more honestly through a coherent beta than through additional internal planning.
- **Kubernetes operation suite:** rejected because operation count is not product depth; a later
  coherent workflow must earn each additional capability under its own owner.
- **Resident process or hosted control plane:** rejected for v0.2 because ADR 0010's pilot trigger
  has not passed and neither is required for the local beta promise.

## Implementation route

Execute exactly one reviewed packet at a time:

1. [KAP-0058](KAP-0058.md) — unify the production lifecycle path;
2. [KAP-0059](KAP-0059.md) — adopt beta surfaces and deepen Application/transport locality;
3. [KAP-0060](KAP-0060.md) — prove `v0.1.1` migration and rollback;
4. [KAP-0064](KAP-0064.md) — finish root release-source locality before qualification;
5. [KAP-0061](KAP-0061.md) — qualify reliability, security, hostile input, and performance;
6. [KAP-0062](KAP-0062.md) — produce the exact distribution candidate; and
7. [KAP-0063](KAP-0063.md) — independently accept, publish, verify, and hand off website claims.

KAP-0064 was inserted after migration work demonstrated that source-locality changes must precede a
frozen qualification baseline. It does not widen the selected release unit or product promise.

The sequence may stop on an unresolved correctness or security blocker. It may not silently add a
capability, public seam, package, target, sandbox dependency, or production claim.

## Acceptance

- The selected route and rejected alternatives are explicit.
- The route is justified as a maintainer technology bet, not disguised external evidence.
- `docs/V0.2.md` defines a finite release and compatibility posture.
- Every implementation category has one bounded task owner and ordered gate.
- KAP-0038 semantics and `UNKNOWN` remain unchanged.
- The sandbox remains paused and outside the distributed release.
- KAP-0047 becomes post-beta evidence rather than a pre-implementation requirement.
- No private company record or commercial rationale enters the technical decision.

## Non-goals

No assertion that users demanded v0.2, production-readiness program, Kubernetes operation catalog,
second provider, generic SDK, daemon, hosted control plane, crates.io publication, sandbox
completion, pricing, launch-channel plan, or automatic continuation after release.

## Next action

Begin [KAP-0058](KAP-0058.md). Do not combine it with compatibility, migration, distribution, or
publication work.

## Residual risk

Maintainer conviction can produce a technically excellent artifact without product pull. The route
contains that risk by keeping v0.2 finite, preserving explicit non-claims, and moving external beta
use to the next direction gate instead of treating more implementation as automatic validation.
