# Deepen Release-Source Locality

Status: active after completed and independently reviewed [KAP-0060](KAP-0060.md), and before
[KAP-0061](KAP-0061.md).

Problem: the root release package remains one deep product module, but migration and hardening have
concentrated independently changing schema/migration, backup/filesystem, lifecycle, receipt, and
test implementation in several long source files. Raw line count is not itself a defect, yet v0.2
should finish source-locality work before qualification freezes a baseline and later structural
churn forces expensive evidence reruns.

Contract owners: [architecture](../docs/ARCHITECTURE.md), [v0.2 release design](../docs/V0.2.md),
KAP-0038, and [V1 technical direction](../docs/VISION.md).

Depends on: accepted KAP-0060 migration, backup, restore, rollback, and downgrade behavior.

## Work

- Inventory root `kapsel` release-source files by owner, independent reason to change, production
  implementation size, test size, and current interface; do not use a line-count threshold as the
  decision rule.
- Keep `Application` and the gateway as deep modules while moving independently changing journal
  schema/migration and backup/filesystem implementation into clearly owned private child modules
  where the KAP-0060 result proves those concerns separable.
- Reassess gateway orchestration, receipt encoding/inspection, publication, and the concrete
  Kubernetes adapter; split only where doing so improves locality behind an existing narrow
  interface rather than creating pass-through modules.
- Keep owner-specific invariant tests adjacent and navigable, whether inline or in private test
  children, without extracting production seams solely for test convenience.
- Preserve compile-time composition, one concrete Kubernetes adapter, private SQL and journal shape,
  exact retained vectors, durable transition ordering, and all supported CLI/MCP behavior.
- Update `ARCHITECTURE.md` only for implementation ownership or dependency-direction changes that
  survive the refactor.

## Acceptance

- Each changed file has one explainable owner and no unrelated independent change axis that should
  live behind an existing private interface.
- The journal retains one private interface while schema/migration and backup/filesystem behavior
  have explicit implementation locality; callers cannot select storage or sequence durable states.
- Gateway lifecycle orchestration and receipt construction/inspection remain deep rather than being
  spread across shallow pass-through modules.
- Exact `v0.1.1` migration, backup, restore, downgrade, grant, and receipt vectors remain
  state-for-state and byte-for-byte accepted.
- No public Rust compatibility promise, crate, generic storage/provider interface, runtime plugin,
  second adapter, capability, or sandbox dependency appears.
- Focused lifecycle, migration, receipt, CLI/MCP, Clippy, formatting, default gate, and fresh
  architecture/locality review pass before KAP-0061 freezes its qualification baseline.

## Non-goals

No sandbox decomposition, arbitrary maximum file length, behavior redesign, SQL compatibility
promise, migration-policy change, receipt-format change, performance qualification, packaging,
version bump, or publication.

## Next action

Hand the accepted, structurally stable root release source to [KAP-0061](KAP-0061.md) for finite
qualification and baseline freezing.

## Residual risk

Moving private Rust implementation can create visibility churn or hide accidental coupling without
changing test results. The packet therefore requires owner-oriented review in addition to unchanged
behavioral evidence; it cannot prove that future growth will not require another locality pass.
