# Deepen Release Artifact Tooling

Status: post-release. Begin only after verified v0.2.0 publication.

Problem: deterministic assembly, bounded archive parsing and extraction, metadata and SBOM
construction, digest handling, artifact smoke, reproducibility, and upgrade proof are spread across
several Python programs. Repeated archive and identity rules form an unnamed tooling module with
weak locality.

Contract owners: [release artifacts](../docs/RELEASE.md), [build](../docs/BUILD.md), and
[V1 technical direction](../docs/VISION.md).

Depends on: verified v0.2.0 publication and preservation of its exact artifacts, vectors, and
evidence.

## Work

- Inventory repeated release invariants and map each to assembly, verification, reproducibility,
  upgrade, or independent black-box evidence.
- Deepen the existing unpublished `kapsel-dev` package with one typed release-artifact tooling
  module; do not create another product package.
- Move stable behavior incrementally behind golden archive, metadata, SBOM, digest, and rejection
  vectors rather than rewriting every script at once.
- Preserve bounded parsing, exclusive extraction, deterministic serialization, clean-environment
  execution, and explicit subprocess failures.
- Retain at least one verifier independent of the product implementation so assembly and
  verification do not merely repeat the same defect.
- Remove superseded Python only after exact old/new output and rejection parity passes.

## Acceptance

- One deep tooling interface owns normalized assembly, exact layout, bounded extraction, metadata,
  SBOM, digest-manifest, and artifact-verification invariants.
- Deleting that module would redistribute substantive release knowledge across callers rather than
  remove a pass-through.
- Published v0.2.0 artifacts and evidence remain byte-for-byte immutable.
- Golden valid and hostile vectors, two-build reproducibility, extracted-artifact smoke, upgrade,
  rollback, cleanup, and independent verification pass.
- Normal Kapsel runtime gains no tooling dependency and no release-tooling interface becomes a
  supported product interface.

## Non-goals

No capability change, product package split, crates.io publication, generic archive framework,
installer promise, qualification redesign, or rewrite motivated only by language percentage.

## Next action

After publication, freeze the v0.2 release-tooling vectors and choose the smallest
assembly/verification slice that can move behind one `kapsel-dev` interface.

## Residual risk

A shared typed implementation can reproduce one bug consistently across assembly and verification.
Independent fixtures and black-box verification remain required even after locality improves.
