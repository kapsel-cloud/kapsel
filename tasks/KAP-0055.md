# Implement The Provider-Neutral Runner Handoff

Status: implementation candidate and domain-review remediation complete in the working tree;
exact-revision acceptance and the final review gate remain pending. No provider, credential,
resource, image push, spend, endpoint, DNS, or traffic is authorized.

Problem: the accepted Gate 1 runner owns one writable per-run gateway journal and must not mount the
system-state volume, while the existing sandbox `Service::execute_application` and
`Service::reconcile_application` paths also write admission SQLite. KAP-0053 cannot honestly compose
a separate provider runner until one bounded private handoff lets the system service remain the sole
admission-database and receipt-store writer.

Direct owners: [sandbox deployment](../docs/SANDBOX_DEPLOYMENT.md),
[sandbox API](../docs/SANDBOX_API.md), [testing](../docs/TESTING.md),
[threat model](../docs/THREAT_MODEL.md), [privacy](../docs/PRIVACY.md), and the unchanged
[KAP-0038 experiment boundary](../docs/experiments/KAP-0038-kubernetes-effect-gateway-boundary.md).

Depends on: accepted [KAP-0052 service package](KAP-0052.md) and accepted KAP-0053 Authority
Composition Proof. Completion unblocks only the provider-specific GKE execution-composition slice in
[KAP-0053](KAP-0053.md).

## Result

One provider-neutral `kapsel-sandbox` revision runs a separate native runner over a fixed private
handoff. The runner receives one immutable server-owned request and complete operator-owned
`Application` composition, durably marks invocation before calling `Application`, executes or
reconciles the same operation, and returns one terminal report. The system service alone commits
sandbox projection and exact receipt bytes.

This is an offline process and state-transition proof. It is not Kubernetes isolation, provider
identity, managed key custody, network policy, deployment, or public-traffic evidence.

## Fixed boundary

The implementation must preserve these roles:

```text
system service and scheduler
  -> durable admission, policy verification, lease, private handoff authority
       -> separate native runner
            -> one per-run gateway journal
            -> Application::execute or Application::reconcile
       -> authenticated terminal handoff
  -> system service commits public projection and immutable receipt storage
```

The runner never mounts or opens the sandbox admission SQLite database. The system service never
uses the admission database as a KAP-0038 journal. The handoff is a private adapter inside
`kapsel-sandbox`, not a public API, generic queue, provider interface, capability protocol, or
future `kapseld` compatibility surface.

## Work

1. Complete the deployment owner before code with exact bounded schemas for:
   - `application_invoked`: run identity, operation identity, current lease identity, and
     per-run/lease authentication;
   - `application_report.not_attempted`: matching identities plus one exact target rejection and no
     receipt; and
   - `application_report.finalized`: matching identities plus one receiver result, frozen receipt
     digest, and exact frozen receipt bytes.
2. Implement one fixed provider-neutral private transport. Its deterministic process tests use
   loopback or an owner-private local endpoint; it exposes no public sandbox route and performs no
   ambient discovery. Bound frames, fields, receipt bytes, connections, receive time, and response
   time before allocation or state mutation.
3. Generate handoff authority from durable scheduler ownership. Store only the minimum verifier in
   system state, deliver the raw credential through an owner-private runner channel, compare it
   without diagnostic disclosure, and revoke it when the lease is replaced or the run becomes
   inactive.
4. Add only the narrow non-mutating `Application` validation method owned by the deployment
   contract. It reports whether one `AgentRequest` matches the grant already verified by
   `Application::open`; it exposes no grant facts, lifecycle state, or generic authorization seam.
   Project the immutable server-owned request through operator composition and call this method
   before the first invocation marker. Do not duplicate KAP-0038 grant parsing, trust, or tuple
   comparison in `kapsel-sandbox`.
5. Commit `application_invoked` before calling `Application`. A lost acknowledgment permits exact
   replay under the same current lease. After lease expiry, reject the stale runner and let one
   newly authorized recovery lease obtain the existing durable marker.
6. Run `Application::execute` only when no gateway state exists. When gateway state exists or an
   invocation acknowledgment is ambiguous, reopen the same journal and use `Application::reconcile`;
   never blindly resubmit after `apply_started`.
7. Commit a returned terminal report idempotently. Atomically bind the report and receipt digest
   before acknowledging it. Install finalized receipt bytes once through the existing restart-safe
   publication protocol. Reject changed report fields, digest, bytes, operation, run, lease, or
   credential. Keep `not_attempted` receipt-free.
8. Update the Gate 1 authority composition and mutation harness without replacing historical
   accepted revision/image/digest evidence. Record this slice as a new execution-readiness
   candidate.
9. Add one focused offline command for the handoff process/state proof and document its exact
   non-claims.

## Required tests

Prove at minimum:

- malformed, oversized, duplicate, reordered, unknown, truncated, and trailing handoff fields fail
  before mutation and disclose no input;
- absent, wrong, stale, cross-run, and cross-lease credentials fail closed;
- invocation is durable before the first `Application` call and exact lost-ack replay adds no second
  transition;
- lease expiry rejects the old runner, one recovery lease resumes the same operation, and gateway
  state forces reconcile rather than blind execute;
- process loss before invocation, after invocation acknowledgment, after `apply_started`, after a
  terminal report, and on both sides of receipt publication converges under one run/operation;
- `not_attempted` commits one rejection without receipt bytes or receiver result;
- each `SUCCEEDED`, `FAILED`, and `UNKNOWN` report preserves unchanged KAP-0038 meaning and exact
  receipt bytes;
- mismatched report or receipt replay is rejected even across restart and concurrency;
- timeout, disconnect, handoff status, lease loss, storage error, and receipt-publication failure do
  not manufacture or alter a receiver result;
- the runner configuration receives no system-state path, never attempts to open system SQLite, and
  the locked runner composition contains no system-state mount; the system process does not mount a
  per-run journal; and
- tests perform no provider command, credential lookup, network call beyond their owned local
  fixture, endpoint publication, DNS change, or public request.

## Implementation candidate evidence

The candidate adds one exact private TCP binary handoff, per-lease credential verifier rotation,
transactionally fenced invocation/report commits, semantic report replay binding, and a separate
native `runner` mode. `Application` changes only by one non-mutating exact request/grant match. The
system remains the only admission SQLite and immutable receipt writer; the runner grammar has no
system-state argument and opens one run journal/outbox plus read-only composition/handoff inputs.
The production subprocess proof starts both native modes over deployment-faithful projected symlinks
and an empty gateway volume, covers receipt-free plus actual KAP-0038 `SUCCEEDED` and `UNKNOWN`
deterministic Kubernetes paths, and proves exact system receipt installation, separate state
ownership, and separately trusted receipt inspection/classifier agreement. The actual `FAILED`
Application path crosses the exact handoff adapter in the service contract and now proves the same
byte identity and classifier agreement. Direct listener tests reject an oversized frame and
oversized receipt field before invocation/report mutation. Production process-kill tests cover loss
before invocation, after the durable invocation ACK, after `apply_started` with reconcile-only
recovery, and after a durable terminal report with system restart and exact replay. The two
package-private receipt-publication tests own the narrower crash boundaries: restart with a durable
claim before final object installation, and restart after final-object installation but before
availability commit. Focused tests additionally lock escape/substitution denial, the absolute
trickle-resistant receive deadline, transaction-time lease expiry, pending finalized recovery across
public expiry, capacity release, and credential Debug redaction.

The focused command is `cargo make test-sandbox-runner-handoff`. Gate 1 retains its historical
accepted fixture digest and records the changed topology as an unreviewed execution-readiness

## Residual risk

A correct local handoff can prove authority separation, restart idempotency, and projection
ordering; it cannot prove private-cluster reachability, Kubernetes identity enforcement, runtime/CNI
isolation, managed key custody, storage fencing, provider audit behavior, cleanup, cost, or public
safety. Those remain KAP-0053 evidence.
