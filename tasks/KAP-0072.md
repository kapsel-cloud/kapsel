# Narrow The Public Sandbox To The Real Runner-Loss Proof

Status: completed direction correction. Gate 1 item 1 deleted backup/restore; KAP-0070 later closed
through this packet's explicit fallback, and KAP-0073 retires the deployable sandbox. This packet
authorizes no resumed implementation, provider, credential, resource, spend, image, endpoint, DNS,
private-live command, or public traffic.

Problem: KAP-0069 correctly removed the remote-controller topology but retained controller-host
continuity, replacement-host restore, backup generations, and thirteen nonclean reconstruction
states as product-essential. The resulting sandbox became a disaster-recoverable anonymous hosted
system rather than the finite website proof that motivated it. Exact checkpoint
`bde1e3ba72058d2ca5787fbe8cc018cc8ced1da2` proves the clean backup replacement and restore design is
technically feasible, but completing its remaining matrix would not materially test whether
customer-resident Kapsel is useful enough to install.

## Decision

The sandbox has one job:

> Let a visitor run the real Kapsel effect lifecycle against fixed synthetic Kubernetes state,
> observe intentional runner-process loss and same-operation reconciliation without a blind second
> mutation, and inspect the real frozen receipt.

Retain:

- the fixed public `v1` scenario and projection vocabulary, subject to its explicit
  host/storage-loss availability limit;
- the real root `Application`, exact server-owned authorization, real synthetic conditional
  mutation, receiver classification, and frozen signed receipt;
- intentional native runner-process loss, stale-process fencing, same-operation reconcile, and no
  blind retry after `apply_started`;
- separate controller, runner, cleanup, target, key, and operator authority;
- one active reservation through runner retirement and exact UID/owner cleanup absence;
- bounded admission, transport, queue, resource, retention, disclosure, and abuse controls;
- a dedicated synthetic cluster, fixed policy, canary, and unrelated-resource denials; and
- separately authorized private-live and bounded-public gates, including complete teardown and clean
  recreation twice.

Supersede:

- visitor-run continuity across controller-host or controller-storage loss;
- backup generations, replacement generations, backup authority references, backup identity, and
  shipped backup/restore commands;
- replacement-host restoration, host-state rollback, and all thirteen nonclean restore states; and
- any claim that sandbox disaster recovery is representative of the customer-resident product.

Runner-process loss and controller-process restart with the same validated state remain owned
recovery seams. Controller-host or controller-storage loss is instead a catastrophic sandbox
availability failure:

```text
host or state loss/rollback/ambiguity
  -> independently withdraw public traffic
  -> admit and dispatch nothing
  -> manufacture no KAP-0038 or sandbox terminal outcome
  -> revoke fixed authority where still reachable
  -> tear down the complete dedicated synthetic cluster and every owned provider resource
  -> prove cluster, volume, process/cgroup, state-root, endpoint, and DNS absence
  -> create a fresh stopped composition
  -> validate fixed policy, authority, abuse controls, and readiness
  -> explicitly reopen admission through authenticated operator authority
```

An absent database, process, volume, or cluster is not evidence of cleanup or an operation outcome.
If the fixed provider-level inventory cannot prove exact absence independently of the lost
controller database, the endpoint remains withdrawn and the hosted proof is retired. Old locators,
projections, and receipts may be lost before their nominal retention deadline and are not
reconstructed.

The same-origin edge or equivalent exposure owner must hold an independently usable traffic-cutoff
mechanism and automatic exposure expiry. It cannot rely on the controller database or claim to
cancel, classify, or clean an admitted operation.

## Implementation order

1. Remove the superseded backup/restore implementation, schema, bridge, tests, planned command
   grammar, and documentation while preserving the retained matrices.
2. Prove controller-process restart with the same validated state remains distinct from runner loss
   and catastrophic host/storage loss.
3. Add a deterministic catastrophic-loss state machine that appends no result, receipt,
   `service_failed`, `not_attempted`, cleanup absence, or capacity-release fact.
4. Compose and test the required same-origin edge as the authoritative per-source abuse mechanism.
   Freeze its private authenticated edge-to-native channel, deny direct public native access, strip
   visitor forwarding/source headers, enforce bounded request/window/burst and memory before
   forwarding, and store no raw source identity in run state or public output.
5. Freeze the provider-independent inventory and operator absence/readiness/reopen procedure needed
   when controller state is unavailable.
6. Produce the smallest authenticated host bundle and private-live fixture needed for the retained
   proof. Do not restore the deleted disaster-recovery scope.
7. Pass fresh correctness, security, privacy, and architecture review before requesting any next
   authorization gate.

## Acceptance

- The real `Application`, process-loss seam, same-operation reconciliation, exact result vocabulary,
  receipt, and cleanup remain unchanged.
- Public `v1` JSON bytes remain fixture-compatible; its availability semantics explicitly exclude
  controller-host/storage loss.
- Host/storage loss withdraws traffic independently, creates no lifecycle/result/receipt/cleanup
  fact, and cannot initialize against a possibly surviving old cluster.
- Complete independent provider/cluster/state absence precedes clean stopped initialization;
  readiness and explicit authenticated reopen precede admission.
- One active reservation remains held through exact cleanup absence while state is intact.
- One real bounded abuse-control composition rejects before admission without public or durable raw
  source identity.
- Backup/restore, replacement-host, thirteen-state reconstruction, and backup-only interfaces are
  absent from the active route.
- The package graph remains `kapsel-sandbox -> kapsel`; no generic storage/provider/queue interface,
  resident process, second capability, or production claim appears.
- The exact narrowed revision passes focused sandbox lanes, the complete default gate, and fresh
  independent review before Gate 2 is considered.

## Residual risk

The narrowed proof still runs anonymous input through a native host and real synthetic Kubernetes
mutation. The controller is a concentrated compromise and availability point; OS identities are not
hard isolation; distributed abuse can deny availability; cleanup can stall and hold cost/capacity;
provider records can outlive logical deletion; and host/storage loss can erase admitted public
projection and receipts. Passing this packet proves only product comprehension of runner-process
recovery, not customer-resident utility or production safety.
