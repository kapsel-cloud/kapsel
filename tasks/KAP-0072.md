# Remove Sandbox Backup And Restore Scope

Status: complete and historical. The sandbox backup/restore branch and its expanded state grammar
were removed before the sandbox itself was retired.

Owners: [historical sandbox deployment](../docs/SANDBOX_DEPLOYMENT.md), [KAP-0070](KAP-0070.md), and
[sandbox removal](KAP-0073.md).

## Decision

The hosted experiment did not need controller-host replacement, backup generations, restore across
thirteen non-clean states, or host-state rollback to demonstrate process-loss recovery. Those
surfaces multiplied authority, storage, cleanup, and failure-state contracts without changing the
root KAP-0038 mechanism.

The retained sandbox scope kept:

- one serialized active run;
- fixed public request and projection fixtures;
- native runner process-loss recovery;
- one dedicated synthetic cluster and exact policy;
- bounded cleanup and absence evidence; and
- explicit teardown and recreation behavior.

It removed:

- backup generation and manifest schemas;
- replacement-host restoration;
- host-state rollback;
- restore-specific authority and cleanup paths; and
- every claim of controller-host continuity.

## Evidence

Archived checkpoint `archive/kap-0070-backup-restore-bde1e3b` preserves the removed design. Deletion
revision `5d55e67` removed the backup owner, schema, state-root grammar, backup-only tests, and root
schema-digest bridge while focused sandbox and default gates remained green.

## Acceptance

- Root `Application` lifecycle and receipt semantics are unchanged.
- Sandbox runner-process recovery remains independent of controller-host continuity.
- No backup/restore code or compatibility promise remains active.
- Historical backup evidence is clearly non-deployable.

## Residual risk

The narrowed sandbox did not provide host-loss continuity or disaster recovery. KAP-0070 later
closed through offline fallback, and KAP-0073 removed the deployable sandbox.
