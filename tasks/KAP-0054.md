# Select The First Customer-Resident Preview Boundary

Status: queued decision after KAP-0069 and exact public-proof acceptance. An explicit maintainer
product-scope decision reopens the resident question before an external workflow exists so Kapsel
can specify one installable non-production product preview. This revises the previous evidence-first
decision gate; it does not authorize implementation, a daemon, a transport, a package, or production
compatibility.

Problem: the verified mechanism is available only through the local CLI and stdio MCP process. Those
may already be the smallest safe customer-controlled integration, or one resident process may be
necessary for durable caller-independent operation, repeated invocation, health, and lifecycle. The
public sandbox cannot select that boundary, and private strategy must not prescribe it.

Direct owners: [V1 technical direction](../docs/VISION.md), [technical scope](../docs/SCOPE.md),
[architecture](../docs/ARCHITECTURE.md), [testing](../docs/TESTING.md), and the finite preview owner
created only if this packet selects implementation.

Depends on: verified v0.2.0 publication, completed [KAP-0069](KAP-0069.md) route selection, and
exact acceptance of the selected public proof. Approved aggregate KAP-0047 findings may inform the
decision but are not a prerequisite. Private customer, buyer, pricing, acquisition, and company
rationale remain outside this repository.

## Required preview

The selected boundary must support one customer-controlled non-production integration for the sole
`kubernetes.set_deployment_image` capability while keeping credentials, grants, trust, signing
material, durable state, and receiver truth operator-controlled. It must provide stable operation
identity, restart recovery, bounded result/status, and receipt retrieval without giving the caller
Kubernetes mutation authority.

## Decision work

1. Define one representative customer-controlled non-production integration: caller, target,
   operator authority model, operation identity, restart behavior, installation boundary, recovery
   need, and finite support window using public technical facts only.
2. Decide whether the existing CLI or stdio MCP process satisfies the workflow with less operational
   risk.
3. Only if they are insufficient, decide whether one resident process is justified and define its
   one-way dependency on `kapsel` without duplicating effect lifecycle or classification.
4. Select exactly one local caller boundary and specify operation identity, replay, reconnect,
   cancellation, authorization, versioning, errors, and migration behavior.
5. Select the smallest installation and process model; define configuration, secret handling,
   credential/key rotation, durable storage, health, diagnostics, concurrency, backup, restart,
   upgrade, rollback, downgrade, uninstall, and incident boundaries.
6. Define a finite non-production compatibility and support window. Do not infer production v1 from
   the preview.
7. Produce one implementation packet only if the decision demonstrates why the current process is
   insufficient and why the selected boundary is smaller than rejected alternatives. That packet
   must require a clean installation from versioned instructions without source modification;
   request-only caller authority; recovery of the existing operation identity across executor
   restart; status and receipt retrieval; and installation by another competent operator without
   maintainer shell control.

## Acceptance

- The decision records whether CLI, MCP, or one resident process is selected and why.
- The selected interface serves only the sole existing operation and rejects speculative transports,
  SDKs, and generic capability envelopes.
- Provider credentials and effect authority remain customer-controlled.
- Process, transport, packaging, authentication, storage, RBAC, lifecycle, and caller integration
  are selected by public technical evidence rather than private prescription.
- Every compatibility promise and unsupported interface is explicit.
- Restart, upgrade, rollback, concurrency, rotation, installation, and clean-room preview acceptance
  have finite owners; any implementation packet requires versioned install instructions, no source
  modification, no caller-held Kubernetes mutation credential, identity recovery rather than
  recreation, status and receipt retrieval, and no maintainer shell control.
- Any new package cites a passed extraction trigger and retains one-way dependency ownership.
- One new direction record authorizes exactly one implementation route or records that existing
  CLI/MCP is sufficient and creates none.

## Non-goals

No implementation in this decision packet, standing daemon by assumption, production v1, generic
control plane, hosted customer provider authority, multi-provider platform, arbitrary capability
interface, broad SDK program, managed connection, second operation, or automatic release.

## Next action

Wait for KAP-0069 to select the route and for its exact public proof to pass, then perform this
decision before any resident implementation packet begins.

## Residual risk

Building a preview before a real workflow can encode the wrong transport or lifecycle. Keep the
support window finite, prefer the existing process when it is sufficient, and require retained use
before any production compatibility or broader extraction.
