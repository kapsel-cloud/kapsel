# Select The First Customer-Resident Preview Boundary

Status: complete. This decision selects one minimal customer-resident process because neither the
existing protected CLI nor fixed stdio MCP adapter provides caller-independent lifetime, read-only
status, and exact receipt retrieval across an authority boundary. It creates one gated
implementation packet, [KAP-0074](KAP-0074.md), but authorizes no implementation, customer access,
credential use, production workload, deployment, endpoint, traffic, or compatibility promise.

Direct owners: [V1 technical direction](../docs/VISION.md), [technical scope](../docs/SCOPE.md),
[architecture](../docs/ARCHITECTURE.md), [testing](../docs/TESTING.md), and [KAP-0073](KAP-0073.md).
KAP-0038 remains the sole owner of authorization, effect lifecycle, receiver result, `UNKNOWN`, and
receipt semantics.

## Decision

Select:

```text
existing remediation caller
  -> one authenticated local Unix socket
       -> one `kapseld` executable under a separate OS identity
            -> existing kapsel Application
                 -> existing sole SQLite effect journal
```

The preview remains one pre-authorized `kubernetes.set_deployment_image` operation. The exact grant
binds one operation identity, namespace, Deployment, container, and immutable image digest. This is
one pre-armed non-production rollback or remediation action, not a reusable deployment API.

A protected existing adapter would be smaller, so the decision tested CLI and MCP first. Both retain
the correct exact operation identity and KAP-0038 recovery semantics, but neither meets the complete
workflow. A resident process is necessary only for the missing process lifetime and protected
submit/status/receipt boundary; it must compose `Application` rather than sequence gateway
internals.

## Representative integration

This public representative is a bounded technical preview contract, not evidence of a named customer
or retained use:

- **Caller:** one existing remediation bot running as the dedicated local OS identity
  `kapsel-preview-caller`.
- **Target:** one customer-controlled Kubernetes 1.33 non-production namespace, exact Deployment
  `agent-api`, container `api`, and one immutable rollback image digest selected before install.
- **Authority:** a cluster operator provisions the exact signed grant, authorization trust,
  receipt-signing authority, and an embedded-credential kubeconfig. The Kubernetes identity has only
  namespaced `get` and `patch` on the exact Deployment; Kapsel still fixes the image-only patch
  shape.
- **Ownership:** the locked non-login `kapsel` OS identity owns the process, operator files,
  journal, worker lock, and receipt directory. The caller cannot read or select them.
- **Frequency and disconnect:** the bot may submit the one exact operation occasionally during one
  30-day non-production evaluation and may disconnect immediately after submission. There is no
  schedule, queue, recurring grant, or second operation.
- **Restart and recovery:** systemd owns process start and restart. `kapseld` reconciles the exact
  configured operation once at startup before accepting submissions. The cluster operator owns
  explicit restart after a bounded degraded failure; there is no periodic retry loop.
- **Reconnect:** the bot retains the grant-bound operation identity, reconnects to the same local
  socket, reads the projected status, and retrieves lossless exact receipt bytes plus their SHA-256.
- **Operational consumer:** `UNKNOWN` leaves remediation unresolved and requires cluster-operator
  review. The operator or bot stores the returned receipt outside Kapsel only if its existing
  workflow requires it; offline inspection uses the existing `kapsel inspect` command and separately
  supplied public receipt trust.
- **Boundary:** one exact x86-64 Debian 12 build, systemd, Kubernetes 1.33, one non-production
  installation, and best-effort support during that 30-day evaluation. No production, platform,
  Kubernetes-version, availability, response-time, retention, or future-patch support follows.

If a real installation cannot use this exact pre-armed shape, implementation stops rather than
widening the grant or capability.

## Candidate evidence

Focused source review and existing black-box tests established the following. No privileged host
mutation, account creation, systemd installation, Docker, kind, customer cluster, provider, or
credential was used in this decision.

| Requirement                     | Protected CLI                                           | Protected fixed stdio MCP                                     |
| ------------------------------- | ------------------------------------------------------- | ------------------------------------------------------------- |
| Bounded request-only input      | Pass                                                    | Pass                                                          |
| Stable grant-bound operation ID | Pass                                                    | Pass                                                          |
| Safe same-operation restart     | Pass when another invocation replays the request        | Pass when a new client process replays the request            |
| Separate-identity deployment    | Possible but not specified or proved                    | Schema-safe, but the conventional client-launched shape fails |
| Caller-independent lifetime     | Fail: synchronous process per request                   | Fail: lifetime is attached to stdio                           |
| Startup reconciliation          | Fail: requires another `operate` invocation             | Fail: startup only opens; a tool call triggers execution      |
| Read-only reconnect/status      | Fail: replay advances reconciliation; no status command | Fail: no status tool, task, resource, or subscription         |
| Exact receipt retrieval         | Fail: returns basename and digest only                  | Fail: returns basename and digest only                        |
| Health through caller boundary  | Fail                                                    | Fail                                                          |

The current tests still prove the reusable nucleus: application-owned exact-grant matching, ordinary
CLI/MCP replay, one provider attempt after ambiguous process loss, frozen receipt recovery, and
explicit `SUCCEEDED`, `FAILED`, or `UNKNOWN`. The focused decision gate passed:

```text
cargo test --locked --test application_contract
cargo test --locked --test e2e_operation_command
cargo test --locked --test e2e_mcp_adapter
cargo make test-demo-harness
```

A supervisor around `operate` could hide authority and relaunch the command, but durable stdout
would become an ad hoc status store and copying receipts would become an unsupported retrieval
interface. A protected MCP launcher has the same gaps and cannot reconnect to a prior stdio process.
Extending either adapter with status, receipt, and independent supervision would create the resident
boundary under a misleading old name. Candidate C is therefore the smallest coherent route.

The resident adopts the existing eight-field operator JSON grammar without another parser or
configuration record. Its path values are exactly `/etc/kapsel/grant.bin`,
`/etc/kapsel/authorization.pub`, `/etc/kapsel/kubeconfig.yaml`, `/var/lib/kapsel/journal.sqlite3`,
`/var/lib/kapsel/receipts`, and `/etc/kapsel/receipt.seed`; key identities remain the existing
bounded strings. `/etc/kapsel`, the systemd-owned `/var/lib/kapsel`, and the pre-existing `receipts`
directory are all `kapsel:kapsel-preview-callers` `0700`. Operator files are
`kapsel:kapsel-preview-callers`, regular, single-link, and `0600`. Group members receive no read or
traversal permission; the shared group lets the service verify exact ownership from its fixed
effective GID without an NSS lookup. Journal, worker lock, and receipt files may be absent before
first use; when present they are regular, single-link, service-UID-owned, and `0600`. Existing
KAP-0038 size ceilings remain unchanged.

Every start retains descriptor-relative handles for the fixed configuration, state, and runtime
roots. Read-only operator and receipt bytes come from the validated opened inode. The state root is
not caller-writable; journal opening remains beneath that retained root and verifies the named inode
around SQLite open rather than adding a custom SQLite VFS. Host root, the kernel, and a compromised
`kapsel` service identity remain trusted. Frozen resident receipt paths must remain beneath the
fixed receipt directory; this resident constraint does not change KAP-0038 bytes or Slice 4's
private rotation proof.

The exact ordinary argv is:

```text
/usr/libexec/kapsel/kapseld --operator-config /etc/kapsel/operator.json --socket /run/kapsel/kapseld.sock
```

Only those ordered arguments and exact values are accepted. Ordinary startup has no environment
configuration or finite-connection input and derives the expected caller GID from its systemd-set
effective GID. It serves indefinitely after one startup reconciliation. The unit uses `Type=exec`,
`User=kapsel`, `Group=kapsel-preview-callers`, `RuntimeDirectory=kapsel`,
`RuntimeDirectoryMode=0750`, `StateDirectory=kapsel`, `StateDirectoryMode=0700`, `UMask=0077`,
`Restart=no`, null standard streams, disabled start-rate limiting, and `WantedBy=multi-user.target`.
`Type=exec` does not claim readiness after reconciliation; service state plus successful
authenticated socket use remains the health boundary.

`Restart=no` prevents an automatic same-boot process-restart loop. Every permitted activation—boot,
explicit `start`, or explicit `restart`—attempts startup and reconciliation once. A failed
activation remains failed until another explicit activation or the next enabled boot. Every startup
failure exits 4 without process output; systemd owns the bounded `ActiveState`, `SubState`,
`Result`, `ExecMainCode`, `ExecMainStatus`, and `NRestarts` diagnostics. Runtime-directory cleanup
owns socket removal after every stopped or failed activation. Before bind, `kapseld`
descriptor-relatively removes only an inactive single-link socket with exact service UID,
caller-group GID, and `0660` mode in the expected runtime directory. It refuses every other
stale-path identity without unlinking it and verifies the newly bound socket's exact identity and
mode before admission. After that refusal exits the process, systemd removes the service-owned
runtime directory and its leaf; installed behavior therefore does not promise that a refused leaf
survives manager cleanup.

`kapseld.conf` creates only the locked non-login `kapsel` account, its private same-name group, and
`kapsel-preview-callers`; numeric identities are install-allocated. The operator-owned
`kapsel-preview-caller` account must already exist. Installation adds its supplementary membership,
but the caller's own supervisor must set `Group=kapsel-preview-callers` or perform an equivalent
set-GID-before-exec step because supplementary membership alone is not the authenticated effective
GID. No Kapsel caller unit or wrapper is added.

The direct assets are `crates/kapseld/deploy/kapseld.service` to
`/usr/lib/systemd/system/kapseld.service`, `crates/kapseld/deploy/kapseld.conf` to
`/usr/lib/sysusers.d/kapseld.conf`, and `crates/kapseld/deploy/kapseld-rbac.yaml` to
`/usr/share/kapsel/kapseld-rbac.yaml`. The non-secret manifest contains only
`ServiceAccount/demo/kapsel-preview` with token automount disabled, one exact namespaced Role, and
one RoleBinding. It creates no Namespace, Deployment, Secret, ClusterRole, credential, or workload.
The Role grants only `get` and `patch` on `apps/deployments` with `resourceNames: ["agent-api"]`;
the concrete adapter, not RBAC, owns the patch fields.

Direct operator commands are `systemd-sysusers`, caller-group membership change,
`systemctl daemon-reload`, `enable --now`, `start`, `stop`, `restart`, and `disable --now`. Optional
packaging helpers may invoke those commands later, but no script owns runtime, recovery, status,
receipt, diagnostics, migration, or removal semantics. Uninstall first runs `disable --now` and
waits for process exit and connection closure. It then removes the external caller's supplementary
membership, deletes the RoleBinding and ServiceAccount credential authority, removes the remaining
RBAC objects, and removes executable/unit/sysusers/RBAC/socket artifacts. It deliberately retains
`kapsel`, its private group, `kapsel-preview-callers`, the external caller account, operator files,
journal, and receipts. Destructive data or identity purge is unsupported and must not be presented
as a Kapsel command.

## Complete local vocabulary

The unpublished exact-build interface has three capability-specific requests and no generic
capability envelope:

- `submit_set_deployment_image`: the existing five bounded request fields. One submission may run at
  a time; an overlapping submission returns `BUSY` and is never queued. Caller disconnect does not
  cancel the in-process operation.
- `get_set_deployment_image_status`: operation identity only; reads no Kubernetes state and returns
  only `NOT_FOUND`, `IN_PROGRESS`, `NOT_ATTEMPTED` plus its bounded rejection, or terminal
  `SUCCEEDED`, `FAILED`, or `UNKNOWN`.
- `get_set_deployment_image_receipt`: operation identity only; after finalization returns lowercase
  hexadecimal encoding of the exact frozen receipt bytes plus SHA-256. Before finalization it
  returns `NOT_READY`. Safe reading and digest/path validation stay behind `Application`; `kapseld`
  must not query SQLite or duplicate publication rules.

A frame is exactly a four-byte unsigned big-endian body length followed by that many UTF-8 JSON
bytes. The request length is 1–16 KiB; an ordinary response is at most 16 KiB and a receipt response
at most 40 KiB for the existing 16 KiB receipt ceiling. After its request body, the client must
close its write half within the same two-second read deadline; any additional byte is trailing
input. The server writes one length-prefixed response and closes the connection. At most eight
connections may be accepted. Every response must be written within two seconds; idle, incomplete,
timed-out, excess, unknown, duplicate, malformed, trailing, oversized, and wrong-typed connections
or fields fail closed without lifecycle effect. No request accepts a grant, credential, trust
material, path, lifecycle state, retry choice, shell, manifest, patch, tag, wildcard, admin action,
or second operation. Transport completion, `IN_PROGRESS`, and submission acceptance never become a
receiver result.

## Deletion test and rejected additions

Removing the new resident executable would return process lifetime to the disconnectable caller.
Removing the socket would leave no protected submit/status/receipt path. Removing the systemd unit
or separate identity would leave recovery or authority separation to caller-controlled composition.
Removing narrow application status and exact-receipt reads would force `kapseld` to query SQLite or
private paths. These surfaces are therefore necessary.

Do not add a socket-activation unit, second admin interface, daemon/RPC framework, HTTP/TCP/MCP
server, client SDK, generic envelope, protocol package, second database, cache, queue, scheduler,
controller, lease, background fleet role, dashboard, metrics server, log store, plugin loader,
provider trait, policy engine, container package, sandbox code, or another capability. Service
status and diagnostics remain systemd-owned; there is no socket administration or health request.

## Implementation gate

[KAP-0074](KAP-0074.md) is the only next product packet. It remains gated and requires separate
implementation authorization. Reopen this decision instead of continuing if implementation:

- exceeds 3,000 new or substantially rewritten non-test production-code lines in any language;
- takes more than three weeks before a clean external installation can be attempted;
- deviates materially from this inventory or adds another package, executable, interface, or store;
- requires Python or shell for customer runtime semantics;
- requires a queue, scheduler, controller, periodic reconciliation, public HTTP, remote transport,
  generic abstraction, retired-sandbox reuse, arbitrary provider input, or second capability; or
- cannot preserve exact grant, `apply_started`, observation-only recovery, explicit `UNKNOWN`, and
  frozen receipt behavior through the existing `Application`.

## Decision validation and residual risk

The decision uses existing deterministic evidence plus source-level feasibility review. It does not
prove Unix peer authentication, real separate-UID denial, systemd restart, clean installation,
Kubernetes RBAC, socket bounds, concurrent status during execution, exact receipt retrieval through
the new interface, or uninstall. Those are KAP-0074 acceptance requirements.

The exact operation may be too narrow, GitOps or an existing protected job runner may remain
preferable, and a resident dependency may cost more than its safety value. No external installation,
retained use, production support, broader workflow, buyer, or continuation decision is proved.
