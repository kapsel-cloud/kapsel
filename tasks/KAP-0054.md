# Select The Resident Service Boundary

Status: complete. This decision selects one minimal resident process because neither the existing
CLI nor fixed stdio MCP adapter provides caller-independent lifetime, read-only status, and exact
receipt retrieval across a separate authority boundary.

Direct owners: [V1 technical direction](../docs/VISION.md), [technical scope](../docs/SCOPE.md),
[architecture](../docs/ARCHITECTURE.md), [testing](../docs/TESTING.md), and the
[KAP-0038 experiment boundary](../docs/experiments/KAP-0038-kubernetes-effect-gateway-boundary.md).
KAP-0038 remains the sole owner of authorization, effect lifecycle, receiver result, `UNKNOWN`, and
receipt semantics. [KAP-0074](KAP-0074.md) records the implementation.

## Decision

```text
bounded local caller
  -> authenticated Linux Unix socket
       -> kapseld under a separate OS identity
            -> kapsel::Application
                 -> sole SQLite effect journal
```

The interface retains the sole `kubernetes.set_deployment_image` capability. The exact grant binds
one operation identity, namespace, Deployment, container, and immutable image digest. `kapseld`
composes `Application`; it does not sequence gateway internals.

## Why CLI and MCP are insufficient

| Requirement                     | CLI                                             | Fixed stdio MCP                                        |
| ------------------------------- | ----------------------------------------------- | ------------------------------------------------------ |
| Bounded request-only input      | Pass                                            | Pass                                                   |
| Stable grant-bound operation ID | Pass                                            | Pass                                                   |
| Safe same-operation restart     | Pass on replay                                  | Pass from a new client process                         |
| Caller-independent lifetime     | Fail: process is synchronous per request        | Fail: lifetime is attached to stdio                    |
| Startup reconciliation          | Fail: another `operate` invocation is required  | Fail: a tool call is required                          |
| Read-only reconnect/status      | Fail: replay advances reconciliation            | Fail: no status tool, task, or resource                |
| Exact receipt retrieval         | Fail: returns basename and digest only          | Fail: returns basename and digest only                 |
| Separate authority identity     | Possible but not specified as an installed path | Conventional client-launched shape does not provide it |

Wrapping either adapter would create unsupported status storage, receipt copying, and supervision.
The resident process is the smallest coherent owner for independent lifetime and the protected
submit/status/receipt boundary.

## Authority and filesystem

The resident reuses the root operator JSON grammar. Its exact paths are:

```text
/etc/kapsel/operator.json
/etc/kapsel/grant.bin
/etc/kapsel/authorization.pub
/etc/kapsel/kubeconfig.yaml
/etc/kapsel/receipt.seed
/var/lib/kapsel/journal.sqlite3
/var/lib/kapsel/receipts
```

Configuration and state roots are service-owned mode `0700`; operator files are regular,
single-link, service-owned mode `0600`. The caller group receives no read or traversal permission.
Journal, worker lock, and receipt files may be absent before first use; when present they remain
regular, single-link, service-owned mode `0600`.

Startup retains descriptor-relative handles for configuration, state, receipt, and runtime roots.
Authority and receipt reads use validated opened inodes. Frozen resident receipt paths remain
beneath the fixed receipt directory. Host root, the kernel, and the service identity remain trusted.

## Process lifecycle

The exact argv is:

```text
/usr/libexec/kapsel/kapseld --operator-config /etc/kapsel/operator.json --socket /run/kapsel/kapseld.sock
```

Ordinary startup accepts no environment configuration or finite-connection input. It reconciles once
before binding and then serves indefinitely. The systemd unit uses `Type=exec`, `User=kapsel`,
`Group=kapsel-preview-callers`, `RuntimeDirectory=kapsel`, `RuntimeDirectoryMode=0750`,
`StateDirectory=kapsel`, `StateDirectoryMode=0700`, `UMask=0077`, `Restart=no`, null standard
streams, disabled start-rate limiting, and `WantedBy=multi-user.target`.

Every boot, explicit start, or explicit restart attempts startup once. There is no periodic retry or
automatic same-boot restart loop. Systemd owns runtime-directory cleanup, service state, and bounded
diagnostics. Before bind, `kapseld` removes only an inactive single-link socket with exact service
UID, caller-group GID, and mode `0660`; it leaves every other leaf unchanged and fails. Systemd may
then remove the runtime directory and leaf.

The sysusers record creates only `kapsel`, its private group, and `kapsel-preview-callers`. It does
not create the caller. The caller process must have effective group `kapsel-preview-callers`;
supplementary membership alone is not authenticated.

## Interface vocabulary

The socket has exactly three capability-specific requests:

- `submit_set_deployment_image`: the existing five request fields; one in-flight submission;
  immediate `BUSY` without queueing; disconnect does not cancel execution.
- `get_set_deployment_image_status`: operation identity only; returns `NOT_FOUND`, `IN_PROGRESS`,
  `NOT_ATTEMPTED` with bounded rejection, `SUCCEEDED`, `FAILED`, or `UNKNOWN` without Kubernetes
  access.
- `get_set_deployment_image_receipt`: operation identity only; returns `NOT_READY` before
  finalization or exact frozen receipt bytes and SHA-256 after finalization.

Frames use a four-byte unsigned big-endian length and UTF-8 JSON body. Request length is 1–16 KiB;
ordinary responses are at most 16 KiB and receipt responses at most 40 KiB. The client must close
its write half within the read deadline. Unknown, duplicate, malformed, trailing, oversized,
timed-out, and wrong-typed input fails closed without lifecycle effect. Transport completion,
`ACCEPTED`, and `IN_PROGRESS` are not receiver results.

## Installation and removal

Static assets install to:

```text
/usr/libexec/kapsel/kapseld
/usr/lib/systemd/system/kapseld.service
/usr/lib/sysusers.d/kapseld.conf
/usr/share/kapsel/kapseld-rbac.yaml
```

The RBAC manifest creates no Namespace, Deployment, Secret, ClusterRole, credential, or workload. It
contains one token-automount-disabled ServiceAccount, one Role with exact Deployment `get`/`patch`,
and one RoleBinding.

Removal stops and disables the service, waits for process and connection closure, removes caller
group membership, revokes Kubernetes authority, and removes installed runtime assets. It retains
identities, operator files, journal, and receipts. Destructive purge is unsupported.

## Rejected additions

Do not add a socket-activation unit, admin interface, daemon/RPC framework, HTTP/TCP/MCP server,
client SDK, generic envelope, protocol package, second database, cache, queue, scheduler,
controller, lease, dashboard, metrics server, plugin loader, provider trait, policy engine,
container package, sandbox code, or another capability. Service status and diagnostics remain
systemd-owned.

## Residual risk

This boundary does not protect against compromised host root, kernel, or service identity. It does
not provide host-loss continuity, backup, HA, broad upgrade/rollback, identity rotation, remote
access, production compatibility, or source-independent distribution.
