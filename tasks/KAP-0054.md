# Select The First Customer-Resident Preview Boundary

Status: active technical decision. KAP-0073 closes the hosted sandbox through fallback and makes
this the sole active product-architecture packet. This packet authorizes no implementation, customer
access, credential use, production workload, daemon, transport, package, or compatibility promise.

Problem: the verified mechanism is available through the local CLI and fixed stdio MCP process, but
Kapsel has no supported customer-resident composition. Those adapters may be safely deployable under
a protected operator identity, or one minimal resident process may be necessary for authority
separation, caller-independent recovery, reconnect, status, and receipt retrieval. The decision must
serve one representative non-production workflow rather than derive architecture from the retired
public sandbox.

Direct owners: [V1 technical direction](../docs/VISION.md), [technical scope](../docs/SCOPE.md),
[architecture](../docs/ARCHITECTURE.md), [testing](../docs/TESTING.md), and [KAP-0073](KAP-0073.md).
KAP-0038 remains the sole owner of authorization, effect lifecycle, receiver result, `UNKNOWN`, and
receipt semantics.

Depends on: verified v0.2.0 publication and accepted KAP-0073 direction. It does not depend on
sandbox deletion completing and may be researched in parallel, but no resident implementation packet
may begin until the sandbox deletion leaves one clean active workspace and this decision is
accepted.

## Focused target

Select the smallest customer-controlled, non-production installation for one pre-authorized
`kubernetes.set_deployment_image` operation. The customer holds Kubernetes credentials, grant trust,
signing material, journal, and receipts. The caller supplies only bounded intent and cannot read,
select, or inherit operator authority.

The current exact-grant model binds one operation identity, target, container, and immutable image.
Treat that honestly as one pre-armed idempotent rollback or remediation action. Do not silently
widen it into a reusable image-deployment service in this decision.

## Decision work

Complete this decision in several working days:

1. Define one representative integration using public technical facts: existing caller, exact
   non-production target, operator authority, invocation frequency, operation identity, restart
   need, status/receipt consumer, installation owner, and finite support window. Do not include
   private customer identity, commercial terms, or discovery evidence.
2. Test whether the existing CLI or stdio MCP process can run under a separate OS identity so the
   caller cannot read operator configuration, kubeconfig, grant trust, signing material, journal, or
   receipts except through supported request/result interfaces.
3. Determine whether process invocation and stdio can preserve the same operation across caller
   disconnect and executor restart while supporting bounded status and receipt retrieval.
4. Select existing CLI/MCP if it satisfies the workflow with lower operational risk.
5. Only if it is insufficient, select one capability-specific resident process with the smallest
   local authenticated interface. Prefer one Unix-domain socket under filesystem identity controls;
   reject public HTTP, remote transport, generic MCP gateway, SDK, plugin model, or capability
   envelope unless the representative workflow makes the smaller options impossible.
6. Define one versioned installation shape, separate OS identity, exact least-authority Kubernetes
   configuration, paths/modes, start/stop/restart, health, secret-free diagnostics, uninstall, and
   narrow OS/Kubernetes support window.
7. Define operation identity, submit/replay, reconnect/status, receipt retrieval, restart recovery,
   errors, limits, and unsupported behavior without exposing gateway lifecycle sequencing.
8. Produce one implementation packet only if the selected route is installable without source
   modification or standing maintainer shell access and fits a two-to-three-week implementation cap.

## Required preview result

A later implementation may prove only:

- one versioned customer-controlled non-production installation;
- one exact immutable image-change operation;
- operator-held authority inaccessible to the caller;
- stable operation identity;
- restart and same-operation reconciliation without blind mutation;
- bounded `SUCCEEDED`, `FAILED`, or explicit `UNKNOWN`;
- reconnect/status and exact receipt retrieval;
- bounded health and secret-free diagnostics;
- finite start, stop, restart, uninstall, OS, Kubernetes, and support boundaries; and
- clean installation by another competent operator without source changes or standing maintainer
  access.

## Acceptance

- The decision selects CLI, MCP, or one minimal resident process and demonstrates why rejected
  options are either unsafe or larger.
- Caller/authority separation is proved at deployment, not inferred from request-schema omission.
- The selected interface serves only the sole existing operation and exact-grant semantics.
- Customer-held credentials, trust, signing material, journal, and receipts remain local.
- Caller disconnect, executor restart, operation identity, reconnect/status, and receipt retrieval
  have explicit behavior.
- Installation, health, diagnostics, RBAC, lifecycle, uninstall, support, and compatibility are
  finite and non-production.
- One implementation packet fits a two-to-three-week cap and contains no sandbox reuse by default.
- No customer, buyer, price, acquisition, or private evidence enters the public decision.

## Stop conditions

Record that no acceptable preview route exists rather than widen if the representative workflow
requires:

- a generic daemon framework, public HTTP service, Kubernetes operator, or managed control plane;
- multiple capabilities or arbitrary provider input;
- hosted customer credentials or effect execution;
- a policy language, SDK family, plugin system, or generic protocol package;
- major reuse of retired sandbox admission, scheduling, runner-host, staging, or cleanup machinery;
  or
- more than the finite implementation cap before one external installation can be attempted.

## Deferred until retained use

No host-loss continuity, backup, HA, fleet management, production compatibility, broad upgrade
matrix, online key rotation, enterprise identity integration, SIEM/change-management export, managed
coordination, second capability, or v1 release is part of this preview. Each requires retained
external use and a new direction decision.

## Next action

Write the representative integration and compare protected CLI/MCP deployment with one minimal local
resident process. Do not implement while deciding.

## Residual risk

The exact pre-authorized operation may be too narrow, GitOps may remain preferable, receipts may
have no operational consumer, and a resident dependency may cost more to install than its safety
value. Only external installation and retained use can resolve those risks.
