## Fixed implementation unit

Add exactly one unpublished `kapseld -> kapsel` package, one `kapseld` executable, one authenticated
Linux Unix-domain socket, one systemd service unit, and one `sysusers.d` file. The existing KAP-0038
SQLite journal remains the sole lifecycle truth. Expected new or substantially rewritten non-test
production code is 1,200–2,000 lines. Crossing 3,000 lines or three weeks stops work and reopens
KAP-0054.

The accepted runtime, path, identity, Kubernetes RBAC, protocol vocabulary, bounds, status
projection, receipt retrieval, lifecycle commands, uninstall retention rule, support window, and
unsupported failure domains are copied by reference from KAP-0054 and may not drift here.

## Caller and authority contract

- The caller supplies only the existing exact five-field request or an operation identity for
  status/receipt retrieval.
- The locked `kapsel` identity exclusively owns the process, operator files, Kubernetes credential,
  grant trust, receipt signing seed, journal, worker lock, and receipt directory.
- Every start descriptor-relatively opens fixed `/etc/kapsel` and `/var/lib/kapsel` roots, requires
  exact service ownership and `0700` modes, and validates the operator document plus every grant,
  public-key, kubeconfig, signing-seed, journal, worker-lock, receipt-directory, and receipt file as
  the expected `0600` regular single-link file or `0700` directory without symlink traversal. Reads
  use the validated opened inode rather than reopening a pathname.
- The socket parent and mode gate the exact caller group. Every connection must also pass Linux
  kernel peer-credential validation for the expected effective caller group.
- Host root is trusted; no claim is made against a compromised host administrator or kernel.
- The caller never selects or receives an operator path, credential, grant/trust bytes, signing
  material, journal path, receipt path, lifecycle transition, or Kubernetes patch.
- Kubernetes authority is namespaced `get` and `patch` on the exact Deployment. RBAC is not a field
  policy; the existing concrete adapter remains responsible for the fixed conditional image patch.

## Installation and lifecycle contract

The one supported preview is an exact x86-64 Debian 12 build with systemd and Kubernetes 1.33 for
one 30-day non-production evaluation. Install direct artifacts without a required Python or shell
wrapper, provision the static identities, validate exact file ownership/modes, reload systemd, and
`enable --now kapseld.service`. The unit contract is exactly `User=kapsel`,
`Group=kapsel-preview-callers`, `RuntimeDirectory=kapsel`, `RuntimeDirectoryMode=0750`,
`StateDirectory=kapsel`, `StateDirectoryMode=0700`, and `Restart=no`.

On every permitted activation—enabled boot, explicit `start`, or explicit `restart`—`kapseld` opens
the fixed operator configuration and reconciles the exact configured operation once before admitting
submission. It does not periodically retry, and `Restart=no` prevents an automatic same-boot process
restart loop. Configuration, open, or reconciliation failure remains failed until another explicit
activation or the next enabled boot. Runtime-directory cleanup owns normal socket removal. Before
bind, the process descriptor-relatively removes only an exact service-owned socket in the expected
directory and refuses every other stale identity. Caller disconnect does not cancel an accepted
in-process operation. SIGTERM may interrupt at any durable window; the next start uses existing
KAP-0038 recovery. `start`, `stop`, `restart`, `enable --now`, and `disable --now` are systemd
operations.

Uninstall first runs `disable --now` and waits for process exit and connection closure. The operator
then removes the caller from `kapsel-preview-callers`, revokes the preview Kubernetes credential,
and removes unit, sysusers, executable, and socket artifacts while retaining the locked
account/group, operator files, journal, and receipts. Destructive purge is unsupported. No socket
command performs administration, key management, migration, purge, health, or shutdown.

## Test-first vertical slices

1. **Read-only application seam:** add capability-specific projected status and safe exact frozen
   receipt reading behind `Application`. First prove no Kubernetes access, no lifecycle advancement,
   path/digest/byte validation, non-final behavior, and unchanged CLI/MCP contracts.
2. **Bounded authenticated socket:** prove the four-byte big-endian length/body/required client
   write-half-close grammar, duplicate/unknown/oversized/trailing rejection, peer credential
   allow/deny, one exact effective caller group, disclosure bounds, status vocabulary, receipt hex
   round-trip, an eight-connection cap, two-second frame-read/response-write deadlines,
   idle/incomplete close behavior, and saturation without lifecycle effect before wiring submission.
3. **Execution and disconnect:** compose `Application::execute`; prove one in-flight submission,
   `BUSY` without a queue, caller disconnect without cancellation, concurrent reconnect/status, and
   no second provider attempt.
4. **Startup and process loss:** prove startup reconciliation and real process termination at the
   existing mutation and receipt-publication seams, frozen bytes under restart, and explicit
   `UNKNOWN` preservation.
5. **Clean installation:** in a fresh x86-64 Debian 12 systemd environment, prove identities,
   startup descriptor/path checks, caller denial of every operator file, allowed socket use, exact
   RBAC manifest, one reconciliation per boot/start/restart activation, no automatic same-boot
   restart loop, safe stale-socket handling, secret-free systemd diagnostics, stop-before-revocation
   ordering, and uninstall with retained data.
6. **Exact artifact:** assemble one unpublished preview artifact, install without source changes or
   maintainer access, rerun the complete workflow, and independently review architecture and
   security before any external installation is requested.

Use deterministic local Kubernetes fixtures for default tests. Docker/kind, systemd containers or
VMs, and every credential/customer action remain explicit environment gates. Do not weaken a proof
because the local host is macOS.

## Slice 1 implementation record

capability-specific `Application` reads for projected status and exact finalized receipt bytes plus
the journal-frozen SHA-256. The application checks the configured grant-bound operation identity
before any journal lookup. Status and receipt reads use the existing journal snapshot and
publication owners, expose no path, make no Kubernetes request, and advance no lifecycle state.

Focused deterministic evidence covers absent, active, pre-attempt rejection, terminal `SUCCEEDED`,
`FAILED`, and `UNKNOWN`, wrong-identity non-disclosure, exact receipt bytes, non-final `NOT_READY`,

receipt-bearing states require a canonical envelope whose key and classifier-valid statement match
the complete journal-derived frozen facts, and relative receipt roots fail before journal access.
Restrictive umask cannot weaken exact `0600` publication, FIFO substitution cannot block receipt

### Slice 2 exact JSON records

KAP-0054 owns the three request names and transport bounds. This slice fixes the previously missing
concrete JSON records so implementation does not invent a generic envelope or imply submission
acceptance. Object key order is not significant on input; duplicate keys fail closed at every
nesting level. The exact request shapes are:

```json
{"request":"get_set_deployment_image_status","operation_id":"operation-id"}
{"request":"get_set_deployment_image_receipt","operation_id":"operation-id"}
{"request":"submit_set_deployment_image","operation_id":"operation-id","namespace":"demo","deployment":"agent-api","container":"api","immutable_image_digest":"registry.example/agent-api@sha256:0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef"}
```

Status responses contain only `status`, except `NOT_ATTEMPTED` also contains its required
`target_rejection`. Receipt responses are `{"status":"NOT_FOUND"}`, `{"status":"NOT_READY"}`, or a
ready record containing only `status:"READY"`, `receipt_hex`, and `receipt_sha256`. `receipt_hex` is
lowercase hexadecimal of the exact bytes returned by `Application`, and `receipt_sha256` is the
unchanged journal-frozen lowercase digest. The valid Slice 2 submit record returns exactly
`{"status":"ERROR","error_class":"submission_unavailable"}` and performs no `Application` call,
operation creation, Kubernetes access, or lifecycle transition. Slice 3 replaces this temporary
error only when it separately owns execution, disconnect, and `BUSY` semantics.

After authentication and a complete valid frame, malformed JSON, invalid UTF-8, duplicate, unknown,
missing, null, wrong-typed, trailing, cross-request, or out-of-grammar fields receive exactly
`{"status":"ERROR","error_class":"invalid_request"}`. An `Application` read failure receives exactly
`{"status":"ERROR","error_class":"operation_failure"}`. Peer denial, incomplete or invalid framing,
a missed read or write deadline, trailing framed input, saturation, or an unrepresentable over-limit
response closes without a response. None of these errors reflects input, paths, authority, peer
credentials, low-level diagnostics, or receipt bytes.

## Slice 2 implementation record

The candidate adds one unpublished `kapseld -> kapsel` package and one executable. Its deep private
handler checks Linux kernel peer credentials before reading or allocating a caller body, admits at
most eight owned connections through a non-waiting permit after transport accept, and immediately
closes saturation without reading a body, responding, or calling `Application`. It applies one
aggregate two-second frame deadline including required write-half-close, parses one strict
capability-specific JSON record, and calls only the Slice 1 status or receipt read. The synchronous
read runs through Tokio's bounded blocking boundary behind one standard-library mutex so it cannot
block another connection's reactor-owned frame deadline. The handler writes one bounded framed
response under one aggregate two-second deadline and then closes. Exact submit grammar returns only
the temporary `submission_unavailable` error and performs no `Application` call. The package adds
only direct `kapsel`, Serde/JSON, and pinned Tokio `rt,time,net,io-util,sync` dependencies; no
socket, daemon, RPC, queue, protocol, storage, or identity framework is added.

A compile-time `test-harness` feature supplies only a caller-owned temporary socket, expected GID,
finite connection count, and fixed read-only `NOT_FOUND` fixture to the same executable. It is not a
product configuration or distributed service mode. The ordinary Slice 2 executable deliberately has
no startup/configuration composition until the separately gated fixed-root and installation slices
own it.

On 2026-08-15, native x86-64 Linux host `server` (Debian kernel `6.12.48+deb13-amd64`, Rust/Cargo
1.96.1) passed 17 package unit/socket tests and three default real-process allow, comparison-deny,
and saturation tests. One separately invoked ignored test also ran a client through the host's
existing supplementary `docker` group with `sg`: server expected EGID 1000, the caller's genuine
EGID was 992, and the denied client sent no frame and observed prompt close. No identity or group
was mutated. The exact-GID denials closed before body parsing or application access; the allow case
crossed the real executable and one framed status response. Saturation held eight admitted
connections, promptly closed the ninth with no read or response, then served only a new tenth after
one permit was released. The tests also passed exact frame limits, incomplete/trailing/idle and
staged prefix/body/write-half-close behavior under one aggregate deadline, complete and partial
write deadline behavior, authenticated hostile JSON and submit matrices with zero reads, every
status/rejection/receipt/error projection through framed sockets, ordinary/receipt response bounds,
a blocked application read concurrent with another expiring frame, real `Application` read
composition without Kubernetes access, and submit non-effect. macOS package, application, CLI, MCP,
demo-harness, formatting, link, and diff-hygiene gates passed separately; macOS is not claimed as
peer-credential evidence. Slice 2 adds approximately 422 non-test Rust lines and 1,071 test Rust
lines; combined with Slice 1's recorded approximately 698 non-test additions, cumulative KAP-0074
production additions are approximately 1,120, below the 3,000-line stop trigger.

Initial independent review found that saturation queued rather than closed the ninth connection,
synchronous reads could block reactor-owned deadlines, and several public-boundary matrices were
underproved. The sole writer corrected those findings with immediate non-waiting saturation denial,
a bounded blocking read boundary, production-owned aggregate deadline wrappers, complete framed
projection and hostile-input tests, and the distinct-EGID process gate. Three fresh correctness,
Linux-security, and test-quality rereviews found no remaining blocker, high, or medium issue. The
focused package/Clippy, application, CLI, MCP, demo-harness, formatting, links, diff-hygiene, and
complete `./scripts/ci-local.sh` gates passed after correction.

## Acceptance

- Runtime topology is five boxes or fewer and dependency direction remains `kapseld -> kapsel`.
- Only one new package, executable, authenticated interface, systemd unit, and sysusers declaration
  exist; no second state store exists.
- The exact three-request vocabulary and all KAP-0054 bounds are black-box tested.
- Separate identities prove the caller cannot read or select operator authority, state, or receipt
  paths and cannot connect without the exact local authorization.
- Caller loss, service loss, and restart preserve stable operation identity, one provider attempt
  after `apply_started`, observation-only recovery, explicit `UNKNOWN`, and frozen receipt bytes.
- Read-only status and receipt retrieval neither call Kubernetes nor advance lifecycle.
- Exact receipt bytes round-trip through the interface and match the journal-frozen digest without
  exposing the private path.
- Systemd service state and diagnostics are bounded, secret-free, and make no
  provider/result/production claim; the socket has no separate health request.
- A competent operator completes clean install, operation, reconnect, inspection, explicit restart,
  caller/Kubernetes authority revocation, and uninstall without source modification, standing
  maintainer access, Python, or a required shell script.
- Existing `application_contract`, CLI, MCP, receipt, process-kill, default, and explicit live-kind
  gates remain green where their prerequisites apply.
- Fresh independent security and architecture review has no unresolved blocker, high, or medium
  finding.

## Stop conditions

Stop and reopen KAP-0054 if work crosses the line/time cap, needs another runtime surface or store,
cannot serve status during an in-process submission without a queue/controller, needs Python or
shell runtime semantics, duplicates private SQLite/publication behavior, changes KAP-0038 semantics,
requires sandbox reuse, or reveals that the representative workflow needs more than one pre-armed
exact operation.

## Residual risk

Passing this packet would prove only one clean non-production installation. It would not prove
retained use, production safety, operational preference over GitOps, broader workflow fit, support
economics, or demand for another capability.
