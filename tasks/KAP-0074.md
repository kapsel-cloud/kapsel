# Implement The Resident Service Boundary

Status: complete. The unpublished resident service is implemented and qualified through its direct
source-install path. It is not part of the published v0.2.0 artifact and has no production support
or compatibility promise.

Direct owners: [resident architecture decision](KAP-0054.md),
[architecture](../docs/ARCHITECTURE.md), [testing](../docs/TESTING.md), and the
[KAP-0038 experiment boundary](../docs/experiments/KAP-0038-kubernetes-effect-gateway-boundary.md).
KAP-0038 continues to own authorization, lifecycle, receiver result, `UNKNOWN`, and receipt bytes.

## Implementation unit

The implementation adds exactly one unpublished `kapseld -> kapsel` package, one `kapseld`
executable, one authenticated Linux Unix-domain socket, one systemd service unit, one `sysusers.d`
file, and one namespaced RBAC manifest. The existing KAP-0038 SQLite journal remains the sole
lifecycle truth.

```text
bounded local caller
  -> /run/kapsel/kapseld.sock
       -> kapseld
            -> kapsel::Application
                 -> sole SQLite effect journal
                 -> concrete Kubernetes adapter
```

The service adds no scheduler, queue, controller framework, protocol framework, provider
abstraction, policy engine, SDK, or second store.

## Caller and authority boundary

- The caller supplies only the five-field image request or an operation identity for status/receipt
  retrieval.
- The locked `kapsel` identity exclusively owns operator files, Kubernetes credentials, grant trust,
  receipt signing material, journal, worker lock, and receipt directory.
- Startup opens fixed `/etc/kapsel`, `/var/lib/kapsel`, `/var/lib/kapsel/receipts`, and
  `/run/kapsel` roots descriptor-relatively and validates exact owners, modes, regular-file types,
  link counts, path components, and stable consumed bytes.
- The socket is `kapsel:kapsel-preview-callers` mode `0660` beneath a `0750` runtime directory.
  Linux peer credentials must report the expected effective caller-group GID before a frame is read.
- The caller never selects or receives an operator path, credential, grant/trust bytes, signing
  material, journal path, receipt path, lifecycle transition, or Kubernetes patch.
- Kubernetes authority is namespaced `get` and `patch` on exact Deployment `agent-api`. RBAC is not
  a field policy; the concrete adapter remains responsible for the fixed conditional image patch.
- Host root, the kernel, and the `kapsel` service identity remain trusted.

## Protocol

Each connection carries one four-byte big-endian length, one JSON body, required client
write-half-close, one framed response, and close. The aggregate frame-read and response-write
deadlines are two seconds. At most eight connections are admitted; saturation closes immediately
without reading a body or creating lifecycle work.

The exact requests are:

```json
{"request":"get_set_deployment_image_status","operation_id":"operation-id"}
{"request":"get_set_deployment_image_receipt","operation_id":"operation-id"}
{"request":"submit_set_deployment_image","operation_id":"operation-id","namespace":"demo","deployment":"agent-api","container":"api","immutable_image_digest":"registry.example/agent-api@sha256:0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef"}
```

Input key order is insignificant. Duplicate, unknown, missing, null, wrong-typed, trailing,
cross-request, malformed UTF-8, and out-of-grammar fields fail closed.

Status responses contain only `status`, except `NOT_ATTEMPTED`, which also contains its required
`target_rejection`. Receipt responses are `{"status":"NOT_FOUND"}`, `{"status":"NOT_READY"}`, or a
ready record containing only `status:"READY"`, `receipt_hex`, and `receipt_sha256`. The receipt is
lowercase hexadecimal of exact journal-frozen bytes and retains the journal-frozen lowercase digest.

A submission that acquires the sole execution slot, matches the configured grant, and installs the
background execution task returns:

```json
{ "status": "ACCEPTED" }
```

`ACCEPTED` means only that the process owns execution and the in-flight slot. It is not a receiver
result and may precede durable visibility. Disconnect or response failure does not cancel execution.
Completion is observed only through status and receipt requests.

A submission that cannot acquire the slot immediately returns:

```json
{ "status": "BUSY" }
```

`BUSY` waits for nothing, creates no queue, calls no `Application` method, and changes no lifecycle
fact. Invalid requests return `invalid_request`; application or exact-grant failures return the
non-disclosing `operation_failure`. Peer denial, framing failure, timeout, saturation, and an
over-limit response close without a response.

## Execution and startup

One execution `Application` and one projection `Application` may open the same configured operation
and journal. They are two handles to one lifecycle store. Projection reads use the application-owned
status and frozen-receipt grammar and neither call Kubernetes nor advance lifecycle state.

Ordinary `kapseld` accepts only:

```text
--operator-config /etc/kapsel/operator.json --socket /run/kapsel/kapseld.sock
```

It accepts no environment configuration or finite-connection input. Startup opens and reconciles the
execution application once, then opens the projection application, secures the socket, and serves.
There is no periodic retry.

An existing socket leaf is removable only when no listener answers and descriptor-relative metadata
shows an exact single-link socket owned by the service UID and caller-group GID with mode `0660`.
Every other leaf is left unchanged and startup fails. Systemd may then remove the service-owned
runtime directory and its contents. After bind, `kapseld` verifies exact socket type, owner, group,
and mode before admission.

Caller disconnect does not cancel an accepted operation. SIGTERM or process loss may interrupt any
durable window; the next explicit activation uses KAP-0038 recovery. After `apply_started`, recovery
observes and does not issue a blind second mutation attempt.

## Installed assets

| Repository input                          | Direct-install destination                |
| ----------------------------------------- | ----------------------------------------- |
| feature-free `kapseld`                    | `/usr/libexec/kapsel/kapseld`             |
| `crates/kapseld/deploy/kapseld.service`   | `/usr/lib/systemd/system/kapseld.service` |
| `crates/kapseld/deploy/kapseld.conf`      | `/usr/lib/sysusers.d/kapseld.conf`        |
| `crates/kapseld/deploy/kapseld-rbac.yaml` | `/usr/share/kapsel/kapseld-rbac.yaml`     |

The systemd unit uses `Type=exec`, `User=kapsel`, `Group=kapsel-preview-callers`,
`RuntimeDirectory=kapsel`, `RuntimeDirectoryMode=0750`, `StateDirectory=kapsel`,
`StateDirectoryMode=0700`, `UMask=0077`, `Restart=no`, null standard streams, disabled start-rate
limiting, the fixed argv above, and `WantedBy=multi-user.target`.

The sysusers record creates only the locked non-login `kapsel` identity, its private group, and
`kapsel-preview-callers`. It does not create the external caller. The caller's supervisor must set
effective `Group=kapsel-preview-callers`; supplementary membership alone is insufficient.

The RBAC manifest contains one `ServiceAccount/demo/kapsel-preview` with token automount disabled,
one Role granting `apps/deployments` `get` and `patch` for `resourceNames: ["agent-api"]`, and one
RoleBinding. It creates no credential, token Secret, Namespace, Deployment, workload, ClusterRole,
wildcard, or field policy.

Systemd state plus successful authenticated socket use is the health boundary. The socket exposes no
administration, key management, migration, purge, health, or shutdown request. Diagnostics are
limited to `ActiveState`, `SubState`, `Result`, `ExecMainCode`, `ExecMainStatus`, and `NRestarts`.

Uninstall disables and stops the service, waits for process and connection closure, removes caller
group membership, revokes Kubernetes authority, and removes the executable, unit, sysusers record,
RBAC manifest, and runtime socket. It retains identities, operator files, journal, and receipts.
Destructive purge is unsupported.

## Qualification

The deterministic package, application, CLI, MCP, formatting, documentation, Clippy, and default
repository gates pass. Native Linux tests cover peer credentials, saturation, framing deadlines,
process-local execution, disconnect continuity, process loss, startup roots, socket identity, and
static asset bytes.

The direct-source path passed on a fresh x86-64 Debian 12 KVM VM with systemd 252, kind 0.32.0,
kubectl 1.33.13, and Kubernetes v1.33.12. The disposable gate proved:

- clean locked service identity creation and separate caller identity;
- denial of caller access to authority and state files;
- exact-effective-GID admission and supplementary-only denial;
- enabled boot, explicit start/restart, `Restart=no`, and bounded diagnostics;
- process-loss and boot recovery without a second Deployment generation;
- exact stale-socket replacement and refusal behavior;
- named Deployment `get`/`patch` allow cases and denial of decoy, list/watch, other verbs,
  resources, namespaces, and cluster scope;
- one successful image operation preserving Deployment UID and sidecar;
- exact frozen receipt retrieval, offline inspection, replay, and restart;
- ordered caller and Kubernetes authority revocation before asset removal;
- retained operator, journal, and receipt bytes; and
- complete cluster and VM cleanup.

The explicit live-kind gate also passed healthy, `ProgressDeadlineExceeded`, and deleted-after-patch
`UNKNOWN` cases against the pinned node image.

## Acceptance

- Dependency direction remains `kapseld -> kapsel`.
- One package, executable, authenticated interface, systemd unit, sysusers file, RBAC manifest, and
  lifecycle store exist.
- The exact request vocabulary and transport bounds are black-box tested.
- Caller loss, service loss, and restart preserve operation identity, observation-only recovery,
  explicit `UNKNOWN`, and frozen receipt bytes.
- Status and receipt retrieval neither call Kubernetes nor advance lifecycle.
- Systemd diagnostics remain bounded and secret-free.
- Direct source installation, operation, reconnect, inspection, restart, authority revocation, and
  uninstall pass on the qualified environment.

## Unsupported behavior

No published resident artifact, source-independent installation, production use, host-loss
continuity, backup, HA, fleet management, concurrency queue, periodic controller, broad
upgrade/rollback matrix, online key or identity rotation, remote client, container package, SDK,
plugin, second capability, arbitrary image change, arbitrary provider input, hosted authority,
managed coordination, or compatibility promise.

## Residual risk

Qualification covers one direct-source installation on Debian 12/systemd 252 and Kubernetes 1.33. It
does not establish production safety, another platform, artifact identity, upgrade compatibility,
backup, HA, or protection from compromised host root, kernel, or service identity.
