# Retire The Hosted Sandbox And Activate The Resident Decision

Status: accepted direction. This packet closes KAP-0070 through its documented fixtures/local-demo
fallback, commissions removal of deployable sandbox implementation, and makes KAP-0054 the sole
active product-architecture decision. It authorizes no resident implementation, customer work,
provider use, credential access, production workload, deployment, endpoint, DNS, traffic, or second
capability.

Problem: the verified Kapsel mechanism is concentrated in the root product package, while the
unpublished sandbox has grown into a second 28K-line hosted system for anonymous admission,
isolation, scheduling, authority staging, synthetic infrastructure, abuse control, public
projection, and cleanup. Those requirements are legitimate for a public hosted proof but do not
answer whether a customer will install and retain Kapsel. The published local real-process and
disposable-`kind` demonstrations already prove the core process-loss mechanism. Continuing the
sandbox would optimize comprehension infrastructure before proving customer-resident utility.

Direct owners: [technical scope](../docs/SCOPE.md), [architecture](../docs/ARCHITECTURE.md),
[V1 direction](../docs/VISION.md), [testing](../docs/TESTING.md), [build](../docs/BUILD.md),
[KAP-0070](KAP-0070.md), and [KAP-0054](KAP-0054.md). KAP-0038 continues to own authorization,
lifecycle, receiver result, `UNKNOWN`, and receipt semantics.

## Decision

Use KAP-0070's accepted fallback now. Do not implement its remaining Gate 1 items or any live gate.
The active product route becomes one smallest customer-resident, non-production pilot for the sole
`kubernetes.set_deployment_image` capability.

Preserve as active product evidence:

- the root `kapsel` package and deep `Application` interface;
- exact authorization and operator/caller authority separation;
- durable operation identity and pre-attempt facts;
- conditional Kubernetes mutation;
- observation-only same-operation reconciliation after an ambiguous attempt;
- receiver-bounded `SUCCEEDED`, `FAILED`, or explicit `UNKNOWN`;
- frozen signed receipt and offline inspection;
- the published CLI, fixed stdio MCP adapter, real-process harness, disposable-`kind` demonstration,
  release evidence, fixtures, and compatibility commitments.

Retire from the active product route:

- anonymous public admission, reconnectable public run projection, and retention;
- same-origin abuse-edge composition and public traffic control;
- synthetic-cluster scheduling and one-visitor capacity;
- sandbox runner-host identities, cgroups, descriptor handoff, and fixed authority generations;
- sandbox-specific cluster policy, cleanup inventory, catastrophic teardown, and host bundle;
- every provider, private-live, public-exposure, endpoint, DNS, and traffic gate; and
- the unpublished `kapsel-sandbox` package as maintained workspace code.

The sandbox work remains valid historical engineering evidence. It is not a production module, moat
claim, or source for the resident topology. Archive the exact post-backup-deletion checkpoint before
removal. Preserve the existing backup/restore archive tag and enough fixed fixtures and prose to
explain the abandoned public contract without keeping deployable code active.

## Product-maintenance rule

The root package is the product nucleus. Keep its current concrete fusion: one capability, one
durable lifecycle, one Kubernetes adapter, one receiver classifier, and one receipt construction
behind `Application`. Do not split generic core, provider, storage, protocol, policy, receipt, SDK,
or capability packages. A new seam requires a second real adapter, independent deployment need, or
multiple real consumers.

Installation, process lifecycle, health, status, and authority custody are necessary access to the
mechanism, not technical differentiation. Implement only the smallest version needed by an accepted
pilot. Hosted demonstration machinery does not move into root `kapsel` or a resident package.

## Resident-preview minimum

KAP-0054 may select only a route that can eventually prove:

- one versioned installation in a customer-controlled non-production environment;
- customer-held Kubernetes credentials, grant trust, signing material, journal, and receipts;
- a caller that cannot read or select that authority;
- one exact immutable image-change operation and stable operation identity;
- restart recovery without a blind second mutation;
- reconnect or status plus receipt retrieval after caller disconnect;
- bounded health and secret-free diagnostics;
- exact least-authority Kubernetes configuration;
- finite start, stop, restart, uninstall, support, OS, and Kubernetes-version boundaries; and
- clean installation by another competent operator without source modification or standing
  maintainer shell access.

Host-loss continuity, backup, HA, fleet management, production compatibility, broad upgrade
matrices, automated rotation, enterprise identity, SIEM export, managed coordination, another
capability, and generic interfaces remain unearned.

- One exact archive tag preserves the final narrowed sandbox checkpoint before deletion.
- The active workspace contains no deployable sandbox package, deployment asset, build lane, or

  local disposable-cluster demonstration.

- No customer, price, acquisition, buyer, or private company evidence enters this public packet.
- No provider, credential, resource, endpoint, DNS, traffic, resident implementation, production
  claim, or second capability is authorized.

## Stop conditions

Stop the resident route rather than broaden it if the selected preview requires a policy engine,
generic daemon framework, Kubernetes operator, public HTTP service, multiple capabilities, hosted
customer authority, major sandbox reuse, or a new generic package family. Retained external use is
required before production compatibility or another product cycle.

## Next action

Archive and remove the deployable sandbox in one deletion-only packet while preserving the root
product and its release-owned proof. Do not combine that deletion with KAP-0054's resident decision
or implementation.

## Residual risk

The root mechanism still has no retained external installation, demonstrated buyer, production
support, or proof that the exact pre-authorized image operation is useful enough to justify another
resident dependency. Removing the sandbox sacrifices an interactive hosted demonstration but avoids
maintaining a second system that cannot answer those questions.
