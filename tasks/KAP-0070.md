# Prove One Serialized Public Sandbox

Status: active staged implementation and acceptance packet; Contract Correction (Gate 0), Gate 1
Slice 1 serialized capacity/local roles, and Gate 1 Slice 2 native runner host boundary are complete
and accepted. Gate 1 Slices 3–6 remain. KAP-0069 selected one serialized reshape. This packet may
produce offline evidence without external authority. It does not authorize a provider credential,
resource, spend, image push, endpoint, DNS, private live command, or public traffic; each live stage
requires the explicit gate below.

Problem: the fixed sandbox API, deterministic service, real `Application`, separate runner handoff,
and cleanup semantics are accepted offline, but the prior Kubernetes-hosted controller topology is
superseded and no live property is proved. The smallest continuation must run one active operation
at a time from one native controller host into one dedicated synthetic cluster, preserve every
product-essential security and recovery property, and delete the removed remote-controller surface
rather than keeping two deployment routes.

## Finite result

One exact clean revision exposes the unchanged fixed `v1` API through a same-origin boundary. A
visitor can choose `healthy` or `unavailable-image`, receive one durable run identity, reconnect to
the same ordered projection, cross an intentional native runner-process loss, observe no blind
second mutation, retrieve the exact frozen receipt, and observe cleanup separately.

The deployment permits at most one active run, including recovery and cleanup. It contains no
customer workload, customer data, production credential, arbitrary Kubernetes input, second
operation, generic provider/storage/queue seam, account system, dashboard, or resident product
interface.

## Selected topology

```text
same-origin edge or reverse proxy
  -> native controller host
       -> owner-private admission SQLite and immutable receipt directory
       -> serial scheduler, global stop, retention, and UID-safe cleanup
       -> per-run least-privilege runner process
            -> owner-private gateway journal and fixed read-only composition
            -> KAP-0055 authenticated report handoff
            -> real kapsel Application
                 -> dedicated synthetic Kubernetes cluster
                      -> one policy-complete run namespace at a time
```

The controller host is one bounded deployment unit, not a generic control plane. Admission/receipt
state has one writer. Scheduler, retention, and cleanup use local concrete `Service` transitions and
separate fixed Kubernetes credentials; no controller-state listener, controller TLS authority,
`TokenReview`, projected controller token, shared SQLite mount, or Kubernetes key-stager workload
exists.

The runner uses a distinct OS identity, one fresh per-run journal/outbox directory, fixed read-only
request/grant/trust/receipt-signing/Kubernetes/handoff inputs, and no admission database or receipt-
store access. Its credential may patch only its exact UID/owner/resource-version/current-image
matched Deployment through the accepted conditional rule. The target workload receives no runner,
controller, key, store, or cleanup authority.

Serialization is a hard isolation and cost control. Capacity remains held until Kapsel is terminal
or `not_attempted`, exact report/receipt handoff is complete where applicable, and every recorded
cluster object is absent. A subsequent run cannot dispatch while cleanup is incomplete. An operator-
owned canary namespace and retained-state fixtures replace simultaneous visitor-run adversarial
checks; they do not weaken metadata, API, network, volume, key, store, receipt, or unrelated-object
denials.

## Rollback and deletion test

Before exposure, rollback means activate the global stop, preserve retained reads/recovery/receipt
retrieval/cleanup, restore the last accepted host bundle and compatible state, reconcile the one
active operation, and tear down every owned resource after acceptance or rejection. During public
exposure, endpoint and website rollback are separate from host/state/cluster rollback and cannot
change a receiver result.

Delete and retire the hosted proof if any mandatory property requires concurrent runs, a remote
controller plane, a generic storage/provider/queue seam, broader caller authority, customer data,
production credentials, unbounded key export, an unproved runtime/network boundary, an unowned cost
class, or a larger spend/cleanup window than explicitly approved. Also retire if exact teardown and
clean recreation cannot pass twice. Retirement removes the endpoint and deployment artifacts, keeps
only historical evidence needed to explain the decision, preserves the root v0.2 package, and does
not create another sandbox implementation packet.

## Residual risk

The controller host is a concentrated compromise and availability boundary. A compromised runner may
misuse its loaded per-run grant, Kubernetes, or receipt-signing authority; a compromised host may
alter admission, projection, cleanup, or key inputs. OS identities are not hard tenant isolation,
and a sandboxed Kubernetes runtime can still contain defects. Anonymous abuse, provider records,
stuck cleanup, fixed infrastructure cost, and external copying of public receipts remain. Passing
this packet proves only one bounded synthetic demonstration, not production safety, customer-hosted
operation, complete capture, exactly-once mutation, or commercial viability.
