# v0.2.0 Kubernetes effect-gateway beta

Status: published developer-beta contract.

Kind: design.

Authority: v0.2.0 product promise, release unit, compatibility classes, and release acceptance.

Owns: The finite developer-beta release.

Does not own: current `v0.1.1` behavior, exact command or MCP grammar before their owners are
updated, Kubernetes receiver semantics, publication approval, sandbox deployment, or v1.

## Product promise

Kapsel v0.2.0 is a developer beta for one proposition:

> Let an autonomous caller request one authorized Kubernetes Deployment image change without holding
> Kubernetes credentials, then recover from process loss without a blind second mutation and return
> an inspectable `SUCCEEDED`, `FAILED`, or `UNKNOWN` receiver result.

The sole capability remains:

```text
kubernetes.set_deployment_image(namespace, deployment, container, immutable_image_digest)
```

The beta deepens this complete path:

```text
request-only CLI or MCP caller
  -> operator-owned exact grant, trust, Kubernetes authority, journal, and receipt key
  -> durable pre-attempt rejection or mutation marker
  -> one conditional Deployment image-patch opportunity
  -> restart-only receiver observation after ambiguity
  -> frozen classifier-complete signed receipt
  -> bounded offline inspection under separately supplied trust
```

This is a finite technical beta. It does not claim production readiness, exactly-once effects, a
generic Kubernetes toolkit, or compatibility beyond the named v0.2.x surfaces below.

## Release unit

The distributed release is one root `kapsel` archive for `x86_64-unknown-linux-gnu` plus its named
sidecars. It contains:

- the ordinary `kapsel` executable;
- the separately named disposable-kind demonstration executable and owned assets;
- evaluator, compatibility, upgrade, rollback, security, and release documentation;
- release metadata and license; and
- no credentials, grants, private trust decisions, journals, receipts, evaluator output, or provider
  resources.

The exact archive layout, checksums, SBOM, digest manifest, and publisher-authentication sidecar are
adopted by the [release artifact contract](RELEASE.md). A documentation-only candidate replacement
changes source and artifact identity, not that distribution design.

Repository tests, vectors, fuzz targets, scripts, and live-kind gates are supporting evidence, not
runtime distribution surfaces.

The following are adopted for explicit support across v0.2.x. Their direct contract owners freeze
the exact grammar, vectors, and continuity requirements used by every candidate:

| Surface                            | v0.2.x direction                                                                                                                                                  | Direct owner result                                 |
| ---------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------- |
| Capability and lifecycle semantics | Preserve effect-gateway exact authorization, durable attempt, receiver result, explicit `UNKNOWN`, and frozen receipt invariants                                  | effect-gateway vectors retained unchanged           |
| CLI                                | Support the adopted provisioning, operation/restart, and offline-inspection grammar, machine output, bounds, diagnostics, and exit classes                        | `COMMANDS.md` and cross-patch vectors adopted       |
| MCP                                | Support one exact stdio adapter and one `kubernetes.set_deployment_image` tool for the adopted MCP protocol version                                               | `MCP.md` and cross-patch vectors adopted            |
| Grant bytes                        | Continue accepting the v1 exact-grant wire emitted by `v0.1.1`                                                                                                    | effect-gateway grant continuity adopted             |
| Receipt bytes                      | Continue offline inspection of retained v2 receipts emitted by `v0.1.1`; v0.2.x must not re-sign frozen bytes                                                     | effect-gateway retained inspection adopted          |

| Journal upgrade                    | Open or safely migrate an exact `v0.1.1` journal, preserve every durable operation and frozen receipt, and provide explicit rollback or bounded downgrade refusal | Private SQL and complete migration matrix retained  |

Within v0.2.x, intentional incompatible changes to a supported beta surface require an explicit
owner update, migration or replacement guidance, and release notes. Only the latest v0.2.x patch
receives best-effort security and correctness maintenance. There is no response-time, remediation,
platform, or production-support SLA.

## Explicitly unsupported surfaces

The following remain implementation details or separate programs, not v0.2 compatibility surfaces:

- the public Rust exports, module tree, and private adapter seams;
- crates.io, docs.rs, `cargo install`, and source-package layout;
- internal SQL, worker-lock shape, test faults, fixtures, and deterministic provider adapters;
- `kapsel-sandbox`, its HTTP contract, controller protocols, runner handoff, deployment manifests,
  provider resources, and hosted endpoint;
- `kapsel-dev`, fuzz packaging, and repository automation;
- `kapseld`, managed coordination, client SDKs, generic receipt/protocol/storage/provider packages;
- arbitrary shell, `kubectl`, manifest, patch, tag, wildcard, credential, or lifecycle input;
- a second capability or generic Kubernetes/provider interface; and
- macOS, ARM, musl, Windows, or another Linux target without a separately accepted native lane.

Public Rust visibility is retained only as needed by workspace implementation and tests until a
later Cargo-distribution decision explicitly promotes a supported Rust interface.

## Architecture direction

The root `kapsel` package remains one deep, compile-time-composed product module:

- Crash proof crosses the same private operation-selected lifecycle path as production.
- `Application` is the deep module; lifecycle stages remain private where callers do not need them.
- CLI and MCP share private operator composition and domain projection while retaining their own
  framing.
- Exact `v0.1.1` journal, grant, and receipt continuity is proven through upgrade, crash, rollback,
  and bounded downgrade handling.
- The private release source has stable implementation locality and a finite qualification baseline.
- The packaged beta adds no capability, runtime plugin, generic provider interface, daemon, or
  hosted dependency.

The private concrete Kubernetes adapter remains concrete. One production adapter does not justify a
public provider seam. The retired sandbox was never part of the release unit and does not define it.

## Release acceptance

The exact candidate must prove:

- every effect-gateway semantic and denial vector through the single production lifecycle path;
- real process loss at the mutation and receipt-publication seams without a blind second mutation or
  changed frozen bytes;
- healthy, failed-rollout, and bounded-unknown behavior through the ordinary executable and one
  owned disposable-kind demonstration;
- exact CLI and MCP parity for all adopted result, rejection, and error classes;
- `v0.1.1` journal/grant/receipt continuity, migration crash recovery, backup/restore, and the
  chosen downgrade policy;
- bounded malformed and hostile input at every production entry;
- measured local and Kubernetes-wait time, peak resources, journal/receipt growth, and artifact size
  against finite qualification budgets;
- clean assembly, byte-for-byte reproducibility, exact source/binary identity, SBOM and
  vulnerability review, and the adopted publisher-authentication mechanism;
- safe downloaded extraction, install, operation, restart, MCP use, inspection, demonstration,
  cleanup, and uninstall on the sole supported target; and
- fresh architecture, compatibility, security, privacy, and release reviews with no unresolved
  release blocker.

Coverage percentage, checksum agreement, request acceptance, process exit, MCP completion, or demo
completion cannot replace owner-specific proof or strengthen receiver meaning.

## Release summary

The release demonstrates one authorized Kubernetes image change, no caller-held cluster credentials,
durable recovery across process loss, explicit receiver uncertainty, and an inspectable signed
receipt. Every description must preserve the non-production, receiver, receipt, platform, and
compatibility limits.

## Non-goals

No Kubernetes operation suite, arbitrary administration, production-readiness claim, resident
daemon, managed control plane, hosted execution dependency, second capability, generic provider or
storage interface, runtime plugin, public Rust SDK, crates.io release, second platform, or automatic
v1 roadmap.

## Post-release defects

A reproducible finding against the exact v0.2.0 artifact cannot redefine the published release or
widen the sole capability.
