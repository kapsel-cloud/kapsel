# Prospective v0.2.0 release unit

Status: prospective design; not a release authorization or compatibility promise.

Kind: design.

Authority: candidate release unit, surface inventory, unresolved release decisions, and conditional
quality gates.

Owns: what a Stabilize decision could adopt as the finite v0.2.0 design.

Does not own: current 0.1.1 behavior, KAP-0046 direction, implementation, version changes,
publication, sandbox deployment, or v1 promises.

## Decision gate

[KAP-0047](../tasks/KAP-0047.md) supplies approved aggregate evidence from exact `v0.1.1`.
[KAP-0046](../tasks/KAP-0046.md) then chooses exactly one route. This design becomes actionable only
if KAP-0046 chooses **Stabilize** and explicitly adopts or corrects it. Specify, Freeze, or Retire
closes or replaces this design; none leaves an implicit implementation backlog.

Completion of the paused [KAP-0050](../tasks/KAP-0050.md) and [KAP-0053](../tasks/KAP-0053.md)
sandbox proof is neither a prerequisite nor part of the distributed release unit.

## Candidate release unit

The finite candidate distribution is one x86-64 GNU/Linux root archive plus its adjacent checksum
and any separately adopted provenance or attestation sidecars. The archive contains the ordinary
`kapsel` binary, a separately named demonstration harness and its owned assets, evaluator/release
documentation, release metadata, and the license. A post-Stabilize distribution packet must select
and name every sidecar before adoption.

```text
Distributed:
  kapsel root archive for x86_64-unknown-linux-gnu
  ordinary kapsel binary
  separately named demo harness and owned demo assets
  evaluator/release documentation
  release metadata and license
Adjacent distribution files:
  archive checksum
  provenance or attestation evidence only if later adopted

Repository evidence, not distributed runtime:
  deterministic tests, vectors, scripts, live-kind gates

Excluded:
  kapsel-sandbox
  kapsel-dev
  fuzz
  provider credentials/resources
  hosted endpoint
  deployment manifests as supported user interface
```

The shared Cargo workspace version does not make unpublished packages, private protocols, SQL
schemas, manifests, source-package contents, or hosted interfaces part of release compatibility. The
assembled archive—not the broader Cargo source package—is the candidate binary distribution.
`x86_64-unknown-linux-gnu` remains the sole candidate target. A second target requires KAP-0047
evidence and a later owner with native build and smoke obligations.

## Migration and rollback design obligations

A Stabilize route must define and test this matrix without making internal SQL public:

- exact `v0.1.1` journal opened by the candidate v0.2.0 binary;
- successful migration followed by idempotent reopen;
- crash before, during, and after schema migration;
- migration backup creation, integrity, restore, and cleanup;
- new binary with old store;
- old binary with migrated store under an explicit support or refusal policy;
- retained `requested`, `authorized`, `not_attempted`, `apply_started`, `receiver_observed`,
  `receipt_prepared`, `receipt_written`, and `finalized` operations;
- receipt preparation/publication crash seams and frozen receipt inspection after upgrade;
- old no-expiry grant acceptance or refusal, trust rotation/revocation, receipt-key
  compromise/rotation, and historical trust availability;
- state-specific key/trust rotation at `requested`, `authorized`, `receiver_observed`, and
  `receipt_prepared`, including fail-closed version/key dispatch and no re-signing of frozen bytes;
- failed release rollout followed by binary and store rollback; and
- explicit, bounded, non-destructive downgrade refusal when downgrade is unsupported.

Each case must state binary version, initial store state, crash point, expected durable state,
provider call count, receipt identity, backup/restore fact, and allowed operator action.

## Performance qualification proposal

Stabilize must measure before setting budgets:

- CLI startup and exact-grant provisioning;
- journal open, submit, and reconcile operations;
- Kubernetes target read, conditional patch request, and observation loop separately;
- receipt construction, publication, and offline inspection;
- ordinary restart and crash recovery;
- peak RSS, CPU time, journal bytes, receipt bytes, and artifact size; and
- cold and warm live-kind demonstration phase timings.

A finite post-Stabilize performance-qualification packet owns the environments, sample counts,
percentiles/maxima, failure ceilings, and acceptance budgets. Every result records environment,
artifact revision, sample count, failure count, input/state class, and percentiles or maxima where
meaningful. Local implementation time and Kubernetes waiting are reported separately. The packet
must select, approve, and pass finite budgets before release; those budgets are not promises until a
compatibility policy says otherwise. A performance timeout must never become receiver `FAILED`,
suppress ambiguity, or hide `UNKNOWN`.

## Conditional implementation slices

Only after KAP-0046 chooses Stabilize may owners instantiate these categories:

1. adopt the final compatibility policy and vectors;
2. implement journal migration and rollback policy;
3. apply evidence-selected correctness and maintainability fixes;
4. qualify reliability and performance;
5. improve supply chain and distribution;
6. build a release candidate and obtain independent acceptance; and
7. publish and verify the downloaded artifact.

This list creates no tasks, estimates, approval, or implementation momentum.

## Explicit non-goals

- no automatic v0.2.0;
- no sandbox completion requirement or hosted endpoint;
- no production-readiness claim;
- no second capability or generic provider interface;
- no daemon, managed control plane, or client SDK;
- no speculative crate extraction;
- no new supported platform without evidence; and
- no compatibility inferred from SemVer, public visibility, or workspace membership.

## Adoption conditions

This design may be adopted only when:

- KAP-0047 records sufficient approved aggregate evidence;
- KAP-0046 chooses Stabilize and cites rejected alternatives;
- every promoted and unsupported surface is explicit;
- KAP-0038 and `SECURITY.md` are explicitly updated before any conflicting wire or support promise,
  and KAP-0048 is satisfied before any Rust/Cargo distribution promise;
- a finite implementation owner and release-acceptance task are created; and
- no unresolved decision is hidden as prose ambiguity.

Until then, current 0.1 owners remain authoritative and their no-compatibility statements remain
unchanged.
